# Ручная раскладка: замер на 1, 2 и 3 нодах

Документ описывает, как провести сравнительный замер скорости инференса одной
и той же модели на разном числе нод, не трогая сами воркеры.

---

## 1. Что изменилось и почему

Loom — маркетплейс, и его планировщик по умолчанию решает сам: брокер взвешивает
спрос, цену и свободную VRAM и выбирает ноды. Для рынка это правильно, а для
замера — бесполезно: сравнение «одна нода против двух против трёх» требует,
чтобы раскладка была **зафиксирована руками** и одинакова между прогонами.

Поэтому запись в каталоге больше не означает «работает».

| | было | стало |
|---|---|---|
| модель в каталоге | брокер разворачивает её сам | предложение, ничего не запускает |
| перезапуск оркестратора | поднимал всё из каталога заново | не запускает ничего |
| выбор нод и слоёв | только брокер | руками, через `Deploy` |
| воркеры | — | запускаются один раз, дальше только оркестратор |

Каталог (`LOOM_MODEL_CATALOG`, по умолчанию `catalog-qwen3-8b.json`) по-прежнему
загружается — но теперь он только наполняет список доступных моделей. Именно
поэтому qwen3-8b больше не поднимается сам при рестарте.

---

## 2. Ноды подключаются один раз

Воркер запускается на ноде один раз и дальше не трогается:

```bash
docker run -d --gpus all --restart unless-stopped \
  -v loom-hf:/root/.cache/huggingface \
  gihpee/loomworker --key loom_<...>
```

Всё остальное — загрузка модели, смена раскладки, снятие — приходит с
оркестратора по управляющему каналу.

### Почему ноды раньше отваливались

Управляющий поток — долгоживущий и почти всегда молчащий. Это ровно тот трафик,
который NAT'ы и туннели рвут, никого не уведомляя: TCP-соединение остаётся
полуоткрытым, воркер продолжает читать поток, у которого другой конец давно
мёртв, никогда не получает ошибку и потому **никогда не переподключается**.
Заметнее всего после перезапуска оркестратора, где корректного закрытия
соединения до воркера часто не доходит.

Лечится keepalive'ом с обеих сторон — пинги отличают живой простаивающий поток
от мёртвого:

- воркер: `GatewayClient.CHANNEL_OPTIONS` (пинг раз в 20 с, таймаут 10 с, плюс
  ограниченный backoff переподключения — чтобы стенд не простаивал минуту);
- оркестратор: те же параметры в `serve_grpc`, включая
  `http2.min_ping_interval_without_data_ms` — иначе сервер сам обрывает клиента
  за «слишком частые» пинги.

### Что делает перезапуск оркестратора

Ничего не запускает — но и ничего не убивает. Свежий оркестратор не помнит
размещений, а воркеры продолжают держать модель. Их heartbeat'ы говорят, что
где загружено, и оркестратор **усыновляет** найденный целиком пайплайн как
размещение (`_adopt_running_model`). Без этого следующий rebalance увидел бы
модель, которую никто не просил, и снёс бы живой пайплайн.

Итог: перезапуск оркестратора посреди эксперимента ничего не стоит, а снять
усыновлённую модель можно кнопкой `снять` на вкладке Deploy.

## 3. Порядок замера

### Шаг 1. Модель в каталог

Вкладка **Models** → HF-имя (например `Qwen/Qwen3-8B`) → бэкенд `shard` →
кнопка `в каталог`. Модель добавлена, но **не запущена**: показывается число
слоёв и сколько их влезает на карту.

### Шаг 2. Развернуть на одной ноде

Вкладка **Deploy**:

1. выбрать модель — рядом показано её число слоёв;
2. выбрать **бэкенд** — для замера на нескольких нодах это `shard`;
3. отметить одну ноду;
4. нажать `разделить поровну между отмеченными` (или вписать число слоёв руками);
5. `развернуть`.

Строка под кнопками считает сумму вживую: `n1=36 = 36 из 36 ✓`. Пока сумма не
совпадает с числом слоёв модели, развернуть не получится — и это проверяется
**до** того, как что-то начнёт скачиваться.

### Шаг 3. Замерить

Вкладка **Console** — отправить запрос, снять статистику: tok/s (decode), TTFT,
время между токенами, разбивку «свои слои / остальные стадии / транспорт».
История прогонов сохраняется в браузере, так что цифры прошлого шага никуда не
денутся.

### Шаг 4. Две ноды, потом три

Вернуться в **Deploy**, отметить вторую ноду, `разделить поровну`, `развернуть`.
Переразвёртывание одной командой: старые стадии снимаются, новые ставятся —
руками ничего чистить не надо. Замерить. Затем то же с третьей.

---

## 4. Что проверяется до запуска

Раскладка проверяется целиком перед тем, как хоть один воркер начнёт качать
веса. Отказ — это строка на экране, а не падение через двадцать минут.

| проблема | что покажет |
|---|---|
| сумма не сходится | `the stages cover 36 of 40 layers (4 missing)` |
| дырка между стадиями | `a gap of 4 layers between n1 (ends at 8) and n2 (starts at 12)` |
| перекрытие | `an overlap of 4 layers between n1 and n2` |
| не с нулевого слоя | `the first stage must start at layer 0` |
| нода дважды | `node n1 appears twice; one node is one stage of a pipeline` |
| ноды нет в сети | `not connected right now: n7. Connected nodes: n1, n2` |
| не влезет по VRAM | `n1: 30 layers need about 21.4 GB but the node reports 14.2 GB free` |

Последнюю проверку можно перебить кнопкой `развернуть, игнорируя оценку VRAM`
(в API — `force: true`): оценка консервативна, и оператор может знать лучше.
Остальные — не проверки стиля, а условия работоспособности: дырка означает, что
пайплайн считает несуществующую модель, перекрытие — что активации дважды
проходят одни и те же слои.

---

## 5. Бэкенд выбирается на деплое, а не в каталоге

Запись в каталоге говорит, **что** за модель; как её обслуживать — свойство
прогона. Один и тот же чекпоинт `vllm` отдаёт целиком, а `shard` режет по
слоям, и переключаться между ними надо без правки файла каталога и перезапуска
оркестратора. Поэтому бэкенд задаётся в форме Deploy (в API — поле
`backend_type`) и перекрывает каталожный только для этого развёртывания.

**Разложить по нодам умеют не все.** `vllm`, `sglang`, `mlx` загружают модель
целиком и отвечают на полные запросы — стадией пайплайна они быть не могут:

| бэкенд | режется по слоям |
|---|---|
| `shard` | да — transformers, работает везде, включая CPU |
| `vllm_shard` | да — vLLM, только CUDA, нужен образ `loomworker-vllm` |
| `vllm`, `sglang`, `mlx` | нет, только целиком на одну ноду |

Если выбрать неразделяемый бэкенд и отметить две ноды, форма скажет об этом
сразу, ещё до отправки, а сервер откажет второй раз:

```
backend 'vllm' serves whole models only and cannot be split across 2 nodes.
Choose 'shard' (transformers, runs anywhere) or 'vllm_shard' (vLLM, CUDA only)
```

Проверка стоит здесь, а не на нодах, по неприятной причине. Когда каталожная
запись с `backend_type: "vllm"` уехала на три ноды, две отказались при загрузке
— это громко и правильно. А третьей достались слои `[0, 12)`, и старая проверка
их пропускала: она смотрела только на `start_layer`. `vllm serve` диапазон слоёв
игнорирует — он загрузил бы все 36 слоёв и **отвечал бы на полные запросы**,
притворяясь стадией 0, пока остальной пайплайн лежит. Теперь адаптер сверяет
`end_layer` с глубиной модели и отказывается, а агент вдобавок отклоняет любой
не-разделяемый бэкенд в многостадийной роли.

---

## 6. Порядок стадий важен

Порядок отмеченных нод — это порядок пайплайна, а не оформление. Стадия 0
держит эмбеддинги и принимает клиентские запросы, последняя — LM head. На нодах
разной скорости это решает, какая карта несёт эмбеддинги.

Порядок задаётся столбцом `№` в таблице Deploy.

Про сам выбор чисел: **равное деление на неравных нодах — неправильный ответ**
(разбор с цифрами в [VLLM_PIPELINE.md §5c](VLLM_PIPELINE.md)). Пайплайн
последовательный, поэтому темп задаёт медленная нода, и слои имеет смысл
сдвигать в сторону быстрой — насколько позволяет её VRAM. Равное деление здесь
просто нейтральная отправная точка для замера.

## 7. API, если замер скриптуется

```bash
# что развёрнуто и что можно выбрать
curl -H "X-Loom-Admin-Token: $TOKEN" http://ORCH:8000/admin/placement
```

```bash
# развернуть: порядок stages = порядок пайплайна
curl -X POST http://ORCH:8000/admin/deploy \
  -H "X-Loom-Admin-Token: $TOKEN" -H "Content-Type: application/json" \
  -d '{"model_id":"qwen3-8b","backend_type":"shard","stages":[{"node_id":"n1","layers":18},{"node_id":"n2","layers":18}]}'
```

```bash
# снять с нод (в каталоге модель остаётся)
curl -X DELETE http://ORCH:8000/admin/deploy/qwen3-8b -H "X-Loom-Admin-Token: $TOKEN"
```

Вместо `layers` можно задавать явные `start_layer` / `end_layer` — для прогона,
в котором не должно быть никакой неоднозначности. `{"auto": true}` вместо
`stages` возвращает модель под управление брокера: так Loom работает в
продакшене, и для замера это не годится.

---

## 8. Границы

- **Размещения не переживают перезапуск оркестратора сами по себе** — они
  восстанавливаются только усыновлением того, что реально работает на нодах
  (§2). Если воркеры тоже перезапустить, стенд поднимется пустым.
- **Одна нода — одна стадия одного пайплайна.** Двух стадий одной модели на
  одной карте не бывает: нода не может релеить сама себе.
- **Реплики (`target_pipelines`) при ручной раскладке не действуют** — ручное
  размещение описывает ровно один пайплайн. Для нескольких реплик нужен режим
  `auto`.
- **Каталог по умолчанию (`catalog-qwen3-8b.json`) объявляет `vllm`** — то есть
  «целиком на одну карту». Для замера на нескольких нодах выбирайте `shard` в
  форме Deploy; переписывать каталог не нужно. Готовый вариант с `shard` в
  каталоге тоже есть: `LOOM_CATALOG=catalog-qwen3-8b-shard.json`.
- **Ручная раскладка забирает ноду у брокера целиком**: узел, занятый ручным
  размещением, не участвует в планах для остальных моделей — иначе брокер выдал
  бы уже занятую VRAM.
