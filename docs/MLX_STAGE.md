# Мак как стадия пайплайна (MLX / Metal)

Бэкенд `mlx_shard`: Apple Silicon берёт диапазон слоёв модели и работает
стадией наравне с CUDA-нодами. Считает на GPU через Metal.

---

## 1. Почему нативно, а не в контейнере

Проверено на машине, а не по документации:

```
внутри контейнера:  Linux 6.10.14-linuxkit aarch64
                    нет /dev/dri (никакого GPU в контейнере)
нативно:            устройство по умолчанию: Device(gpu, 0)
```

Docker Desktop на macOS запускает контейнеры внутри линуксовой виртуалки.
Metal — фреймворк пользовательского пространства macOS, в Linux его нет и
пробрасывать нечего. Устройства GPU в контейнер не отдаются вообще.

То, что иногда называют обходом, — **libkrun/krunkit** (Podman Desktop): он
даёт гостю virtio-gpu с Venus, то есть **Vulkan**. Для llama.cpp это работает,
для MLX — нет, он написан на Metal-шейдерах.

Поэтому воркер на маке ставится нативно и живёт службой `launchd`. Это даёт те
же два свойства, что `docker run --restart unless-stopped`: установка одной
командой и перезапуск после падения или перезагрузки.

```bash
bash scripts/install_mac_worker.sh --key loom_<...>
```

Или без скрипта, двумя командами:

```bash
python3 -m venv ~/.loom/venv && ~/.loom/venv/bin/pip install "./worker[mlx,p2p]"
~/.loom/venv/bin/loom-worker --key loom_<...>
```

**`[p2p]` здесь не украшение.** Без него нода поднимется и будет работать, но
все активации пойдут через оркестратор — в логе будет `no p2p stack installed`,
а в админке в колонке p2p `relay`. Колесо `lattica` под macOS arm64 есть.

Скрипт проверяет, что python действительно arm64 (под Rosetta колёса MLX
встанут, но GPU за ними не будет), ставит воркер в `~/.loom`, **убеждается,
что MLX реально выбрал GPU**, и регистрирует службу.

---

## 2. Почему не vllm-metal

`vllm-metal` — настоящий официальный плагин (организация `vllm-project`),
считает на GPU мака через MLX, и у него **уже есть pipeline parallelism**:
`apply_pipeline_split()`, `PipelineGroup`, `PipelinedModel` с ровно нашей
семантикой — ранг 0 эмбеддит, последний делает norm и голову.

Не подошёл транспорт. Стадии там общаются через **ring-backend MLX**:
статический `MLX_HOSTFILE` (JSON-список `["ip:port"]` на каждый ранг) плюс
`MLX_RANK`. И приём вшит в сам проход:

```python
if not self._pp.is_first:
    h_in = pipeline_recv(self._pp, ...)
```

Подать состояния аргументом нельзя. Для Loom это несовместимо:

- **статический hostfile на старте** — а раскладку решает оркестратор и меняет
  её на лету;
- **только прямые ip:port** — ни rendezvous, ни пробивания NAT, ни фолбэка на
  релей; вся работа фаз 1–2 обходится стороной;
- **жёсткая группа рангов** — падение одного роняет всю;
- **и решающее: кольцо MLX это мак-с-маком.** Пайплайн из A30 и мака в нём не
  собрать.

Возвращаться к нему стоит, только если замер покажет, что их ядра (paged
attention, тензорные блоки M5) дают существенно больше на батче из одного
токена. Тогда путь — пропатчить `pipeline_recv`/`pipeline_send` под наш
транспорт, ценой патчей внутренностей чужого молодого проекта.

---

## 3. Как это устроено

Модель mlx_lm разрезается тривиально — вот её прямой проход целиком:

```python
h = input_embeddings if input_embeddings is not None else self.embed_tokens(inputs)
mask = create_attention_mask(h, cache[0])
for layer, c in zip(self.layers, cache):
    h = layer(h, mask, c)
return self.norm(h)
```

`self.layers` — обычный список, режется срезом. `input_embeddings=` **уже есть
в сигнатуре**: ровно то, что нужно средней стадии.

Сравните с CUDA-vLLM, где та же возможность потребовала трёх патчей во
внутренности движка (подмена диапазона слоёв, терпимый загрузчик весов,
переклейка ролей pipeline-группы), ручной сборки `SchedulerOutput` и своего
менеджера KV-блоков. **Здесь не патчится ничего.**

### Загрузка только своих весов

```python
load_model(view, lazy=True, strict=False)
```

`strict=False` не спотыкается об отсутствующие веса чужих стадий, `lazy=True`
их не материализует. Указывает на тот же урезанный вид чекпоинта, который уже
строится для vLLM (`shard/loader.py`), — нода качает только те safetensors, в
которых лежат её слои.

### KV-кэш

По объекту `KVCache` на слой на запрос. MLX сам двигает смещение, поэтому
исполнитель не отслеживает позиции — кэш знает, где он.

Освобождение обязательно: память унифицированная, и забытый кэш — это RAM,
которую машина не может использовать ни на что другое.

### Сэмплинг

Сознательно наша арифметика, а не сэмплеры mlx_lm: модель, разрезанная между
маком и CUDA-нодой, должна выбирать токены одинаково независимо от того, где
оказалась последняя стадия.

## 4. Совместимость с CUDA-стадиями

Мак стоит в одном пайплайне с A30 — значит байты на проводе должны совпадать.
Формат несёт dtype вместе с тензором, и обе стороны знают один словарь имён
(`loom_worker/wire.py`).

Проверено в обе стороны, включая bfloat16:

```
mlx  : [-1.8906, 0.4316, 0.9414, 1.9219, …]
torch: [-1.8906, 0.4316, 0.9414, 1.9219, …]
совпало: True      обратно совпало: True
```

MLX-массив читается через buffer protocol (numpy bfloat16 не умеет), torch
собирает те же байты обратно. Ноль конверсий, ноль потерь.

---

## 5. Что проверено

На этой машине, на настоящей модели (`Qwen2.5-0.5B-Instruct-4bit`, 24 слоя):

| проверка | результат |
|---|---|
| две стадии отвечают как целая модель | ✅ токен в токен |
| три стадии — то же самое | ✅ |
| стадия держит только свои слои | ✅ |
| `free` освобождает кэш | ✅ |
| байты совпадают с torch-стадией | ✅ |
| отказ на не-Apple железе | ✅ внятной ошибкой |

Паритет — единственное, на чём всё держится: пайплайн, который считает чуть
иначе, это не более быстрый пайплайн, а сломанный.

---

## 6. Как развернуть

Мак регистрируется как обычная нода. В админке, вкладка **Deploy**:

1. модель;
2. бэкенд **`mlx_shard`**;
3. отметить мак вместе с остальными нодами;
4. слои — руками или «разделить поровну»;
5. развернуть.

Раскладка проверяется до скачивания весов, как и для остальных бэкендов.

**Бэкенд выбирается на каждую стадию.** В таблице Deploy у каждой ноды своя
колонка «бэкенд»; пусто = как у развёртывания. Так мак на `mlx_shard` встаёт
рядом с A30 на `vllm_shard` в одном пайплайне.

Работает это потому, что `LoadShardRequest.backend_type` **всегда был полем на
шард**, а не на модель. То есть ни протокол, ни воркеры менять не пришлось:
каждая нода получает тот движок, который ей назначили, и ведёт себя ровно как
раньше. CUDA-образ не тронут и пересборки не требует.

Приоритет: бэкенд стадии → бэкенд развёртывания → запись в каталоге.

Проверки остались на месте и теперь применяются **к каждой стадии**:

```
stage 1 (node-b) would run backend 'vllm', which serves whole models only
and cannot be one of 2 pipeline stages
```

### Оговорка про старые CUDA-воркеры

Смешанный пайплайн требует, чтобы **обе стороны знали текущий формат провода**.
Воркер, собранный до перехода на bf16, при незнакомом имени dtype молча читал
байты как float32 — а MLX-стадия шлёт bfloat16. Получился бы не сбой, а
правдоподобно неверный ответ.

Если CUDA-воркеры давно не пересобирались, есть два выхода: пересобрать (в
новой версии незнакомый dtype отвергается с внятной ошибкой) или заставить
мак слать во float32 — `LOOM_WIRE_DTYPE=float32` на нём.

## 7. Границы

- **Только Apple Silicon.** На Intel-маке и любом другом железе `prepare()`
  отказывает сразу и говорит, чем пользоваться вместо.
- **Квантованные чекпоинты** (`mlx-community/*-4bit`) работают — mlx_lm читает
  квантизацию из конфига. Смешивать квантованную и неквантованную стадии одной
  модели нельзя.
- **Лимит памяти** мягкий: `mx.set_memory_limit` заставляет рантайм отказывать
  вместо того, чтобы уводить машину в своп. Жёсткая страховка — тот же сторож
  по RSS, что и на остальных бэкендах.
- **Архитектуры**: ищется `model.model.layers` (и пара запасных имён). Если
  архитектура кладёт слои иначе, стадия падает с внятной ошибкой, а не режет
  не тот список.


## Установка на чужой мак — одна строка

```bash
curl -fsSL https://raw.githubusercontent.com/gihpee/loom/main/scripts/install_mac_worker.sh | bash -s -- --key loom_<...>
```

Больше ничего: ни клонирования, ни `git`, ни Xcode. Скрипт сам создаёт
окружение в `~/.loom/venv`, ставит воркер прямо из архива репозитория,
проверяет, что MLX видит GPU, и заводит службу launchd, которая поднимается
при входе в систему и переживает падения — тот же контракт, что даёт
`docker run --restart unless-stopped` на линуксе.

Почему архив, а не `git+https`: `git` на свежем маке — это Xcode command line
tools, несколько гигабайт и диалоговое окно. Для распаковки tarball pip не
нужно ни то, ни другое.

### Что владелец ноды увидит

```
installing from github (main)
installing into /Users/<имя>/.loom
checking the GPU is actually reachable... Device(gpu, 0)

worker installed and started.
  logs:    tail -f ~/.loom/logs/worker.log
  stop:    launchctl bootout gui/501/network.loom.worker
  update:  re-run this same command
```

Строка с `Device(gpu, 0)` — важная: она означает, что MLX действительно вышел
на Metal. Если бы python оказался под Rosetta, колёса MLX встали бы, а GPU за
ними не было бы — и выяснилось бы это сильно позже и невнятно. Скрипт
отказывается работать заранее.

### Обновление и удаление

Обновление — та же команда: pip переустановит воркер, launchd перезапустит.

```bash
launchctl bootout gui/$(id -u)/network.loom.worker
rm ~/Library/LaunchAgents/network.loom.worker.plist
rm -rf ~/.loom
```

### Разработчику

Из чекаута тот же скрипт ставит **этот чекаут**, а не GitHub — определяется по
наличию `worker/pyproject.toml` рядом:

```bash
bash scripts/install_mac_worker.sh --key loom_<...>
```

Ветку можно подменить через `LOOM_BRANCH`, источник целиком — через
`LOOM_SOURCE`, каталог установки — через `LOOM_PREFIX`.

### Чего этот путь не делает

Воркер на маке ставится **нативно, не в докер**, и это не недоработка: Metal —
фреймворк пользовательского пространства macOS, а линуксовый контейнер на маке
живёт в виртуалке, где GPU-устройства нет вовсе. Пробрасывать нечего.
