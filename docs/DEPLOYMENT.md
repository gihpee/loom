# Loom — развёртывание реального стенда (Linux + NVIDIA)

Рунбук для первых продакшн-тестов. Итог: у вас публичный образ воркера, вы
выдаёте ключ, владелец GPU выполняет **одну** команду и больше ничего не делает.

## 0. Что нужно

- **Оркестратор**: любая машина с docker, доступная по TCP-порту с GPU-машин
  (порт 9000 — control plane + туннель данных; 8000 — клиентский API).
- **Воркеры**: Linux + NVIDIA GPU + docker + nvidia-container-toolkit.
  Публичный IP/порты **не нужны** — воркер только исходящее соединение.
- Модель может быть **больше одной карты**: слои режутся между узлами
  (`"backend_type": "shard"`, см. §6a). Если модель влезает на карту целиком —
  быстрее использовать `"vllm"`.

## 1. Публикация образа воркера

```bash
docker build -f docker/worker.cuda.Dockerfile -t gihpee/loomworker:latest worker/
```

```bash
docker push gihpee/loomworker:latest
```

Базовый образ — `vllm/vllm-openai`, поэтому vLLM и CUDA уже внутри. В образе
нет ни планировщика, ни брокера, ни кода оркестратора: только агент
(`worker/`) и protobuf-контракт.

## 2. Запуск оркестратора

Вся конфигурация — в `.env` (compose читает его сам, экспортировать переменные
не нужно). Сгенерировать из шаблона [.env.example](../.env.example):

```bash
bash scripts/init_env.sh
```

Скрипт создаёт `.env` со случайными секретами и печатает admin-токен. Если
порты 8000/9000 заняты — поправьте в `.env`:

```bash
LOOM_HTTP_PORT=18080
LOOM_GRPC_PORT=19090
```

Порт публикуется как `<порт>:<порт>` (одинаковый внутри и снаружи) — номер
попадает в join-ключ воркера, поэтому он обязан совпадать.

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

Адрес подключения указывать НЕ нужно: оркестратор определяет его сам —
публичный IP хоста (через echo-сервис, потому что внутри контейнера виден
только docker-адрес), туннель, или адрес в локальной сети. Переопределить можно
`LOOM_PUBLIC_ADDR` в `.env`.

Проверка + какой адрес получили воркеры:

```bash
curl -s localhost:8000/admin/connect -H "X-Loom-Admin-Token: $LOOM_ADMIN_TOKEN"
```

Поле `dial_address` — это то, что вшивается в ключи; `source` показывает,
откуда он взялся (`env` / `ngrok` / `host-ip` / `loopback`), а `warning`
появляется, если снаружи до него не дозвониться.

## 2a. Если у машины с оркестратором нет публичного IP

Физика: воркер за NAT умеет только звонить наружу, поэтому **одна точка в
системе обязана быть достижимой**. У Parallax эту роль играют вшитые в их код
публичные relay-серверы Gradient (`relay-lattica.gradient.network`) — то есть
адрес там тоже есть, просто чужой. У self-hosted Loom варианты такие:

1. **Воркеры в той же сети** (LAN / VPN / один датацентр) — ничего делать не
   надо: оркестратор сам возьмёт свой сетевой адрес (`source: host-ip`).
2. **Встроенный туннель** — публичная точка входа без публичного IP:

   ```bash
   NGROK_AUTHTOKEN=<токен с ngrok.com> docker compose -f docker-compose.prod.yml --profile tunnel up -d
   ```

   Оркестратор сам спросит у туннеля его публичный `host:port` и подставит в
   ключи. Ключи выдавайте ПОСЛЕ старта туннеля (адрес попадает в ключ на момент
   выдачи).
3. **VPN между машинами** (Tailscale/WireGuard) — задайте адрес в этой сети:
   `LOOM_PUBLIC_ADDR=100.x.y.z:9000`.
4. **Свой публичный адрес** (домен, port-forwarding, дешёвый VPS как точка
   входа) — `LOOM_PUBLIC_ADDR=loom.example.com:9000`.

## 3. Выдача ключа (по одному на машину/владельца)

```bash
curl -s -X POST localhost:8000/admin/keys -H "X-Loom-Admin-Token: $LOOM_ADMIN_TOKEN" -H 'Content-Type: application/json' -d '{"label":"gpu-box-1","max_nodes":1}'
```

Ответ содержит готовую команду:

```json
{
  "key": "loom_eyJpIjoi...",
  "run_command": "docker run -d --gpus all gihpee/loomworker --key loom_eyJpIjoi...",
  "address": "203.0.113.10:9000",
  "max_nodes": 1
}
```

То же кликом: **http://<orchestrator>:8000/admin/ui** → вкладка **Keys**.

Ключ несёт адрес оркестратора и секрет; секрет одновременно является ключом
подписи команд для этого узла, поэтому отзыв ключа лишает узел и возможности
исполнять команды. `max_nodes` ограничивает, сколько машин может привязаться.

## 4. Подключение GPU-машины (всё, что делает владелец)

```bash
docker run -d --gpus all --restart unless-stopped gihpee/loomworker --key loom_eyJpIjoi...
```

Это вся команда. `--gpus all` — требование docker для доступа к картам,
`--restart unless-stopped` — чтобы агент поднимался после перезагрузки; ничего
больше указывать не нужно. (Опционально: `-v loom-hf:/root/.cache/huggingface`
сохранит скачанные веса между пересозданиями контейнера, `-e HF_TOKEN=hf_...`
нужен только для приватных моделей.)

Больше от владельца ничего не требуется: ни портов, ни адресов, ни описания
железа, ни подтверждения размещения моделей. Агент сам:

- определяет GPU (NVML → torch → nvidia-smi): имя карты, число GPU,
  свободный/общий VRAM, TFLOPs и пропускную способность по таблице карт;
- открывает два исходящих стрима (команды + туннель данных);
- по команде оркестратора качает веса, поднимает vLLM с VRAM-квотой,
  рапортует эндпоинт и телеметрию;
- следит за квотой (watchdog) и убивает бэкенд при превышении, не падая сам.

Проверить, что узел в пуле:

```bash
curl -s localhost:8000/admin/nodes -H "X-Loom-Admin-Token: $LOOM_ADMIN_TOKEN"
```

В ответе должно быть `"connected": true`, `"tunnel": true`, реальное имя карты
и `detected_by: "nvml"`.

## 4a. Развернуть модель из админ-панели

Откройте **http://<orchestrator>:8000/admin/ui** → вкладка **Models**:
введите HF-имя (например `Qwen/Qwen3-32B`), выберите бэкенд
(`shard` — можно резать по слоям между узлами, `vllm` — быстрее, но модель
должна влезть на карту), нажмите **deploy**. Архитектура (`num_layers`,
`hidden_size`, MoE/MLA-поля, dtype) вытягивается из `config.json` модели
автоматически — руками ничего заполнять не нужно.

В ответе сразу видно, что определилось и сколько это требует:
слоёв, размер весов, сколько слоёв влезает на карту 24/48/80 ГБ. Если пула не
хватает, модель встанет в состояние `unscheduled` с явной пометкой в таблице —
добавьте узлы или поднимите `LOOM_PARAM_MEM_RATIO`.

Тот же путь через API:

```bash
curl -s -X POST localhost:8000/admin/models/from_hf -H "X-Loom-Admin-Token: $LOOM_ADMIN_TOKEN" -H 'Content-Type: application/json' -d '{"repo":"Qwen/Qwen3-32B","backend_type":"shard","target_pipelines":1}'
```

Наблюдение за оркестрацией — там же в UI: **Nodes** (узлы, автодетект железа,
heartbeat, шарды со статусами), **Models** (стадии пайплайна: `stage 0 [0,16)`,
`stage 1 [16,32)`, … + кнопка remove), **Keys** (адрес подключения и готовая
команда), **Perf-map** (τ/ρ и выбранная Phase-2 цепочка), **SLO / Rebalance**
(кнопка force rebalance), **Console** (отправить запрос и увидеть ответ).

## 5. Первый инференс

Как только брокер разместил модель и vLLM прогрузился (первый раз — минуты,
качаются веса), запрос идёт обычным OpenAI-клиентом:

```bash
curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{"model":"qwen3-8b","messages":[{"role":"user","content":"привет"}]}'
```

Трафик идёт: клиент → API оркестратора → туннель (то самое исходящее
соединение воркера) → vLLM на 127.0.0.1 воркера → назад тем же путём.
Стриминг (`"stream": true`) работает чанками через тот же туннель.

## 6. Сколько VRAM нужно модели

Брокер режет карту по формуле «вес модели / `param_mem_ratio`», остальное
остаётся под KV-кэш. Практические числа для bf16:

| Модель | `LOOM_PARAM_MEM_RATIO=0.6` | `0.75` | `0.85` |
|---|---|---|---|
| Qwen3-0.6B | 1.9 GB | 1.5 GB | 1.3 GB |
| Qwen3-8B | 25.4 GB | 20.3 GB | 17.9 GB |

То есть **Qwen3-8B на карте 24 ГБ требует `LOOM_PARAM_MEM_RATIO=0.75`**
(при 0.6 брокер сочтёт, что модель не влезает, и оставит её `unscheduled`).
Проверить свою модель:

```bash
uv run python -c "import json; from loom.orchestrator.broker import pipeline_vram_bytes; from loom.orchestrator.registry import ModelSpec; s=ModelSpec.from_dict(json.load(open('configs/catalog-qwen3-8b.json'))['models'][0]); print(pipeline_vram_bytes(s.model_info, param_mem_ratio=0.75)/1024**3, 'GB')"
```

Для новой модели скопируйте каталог и заполните `model_info` из HF `config.json`:
`num_layers=num_hidden_layers`, `hidden_dim=hidden_size`,
`intermediate_dim=intermediate_size`, `num_kv_heads=num_key_value_heads`,
`head_size=head_dim`, `tie_embedding=tie_word_embeddings`,
`param_bytes_per_element=2` для bf16/fp16.

## 6a. Модель больше одной карты (многостадийный инференс)

Это ключевой сценарий Loom: модель режется по слоям между узлами. Включается
одной строкой в каталоге — `"backend_type": "shard"` вместо `"vllm"`.

**Сколько карт нужно.** Брокер режет по слоям, поэтому считать надо в слоях:

| Модель (bf16) | Слоёв | Веса | Слоёв на карту 24 GB | Карт нужно |
|---|---|---|---|---|
| Qwen3-8B | 36 | 15.3 GB | 40 (при `0.6`) | 1 — многостадийность не нужна |
| Qwen3-32B | 64 | 61 GB | 15 / 19 / 22 (`0.6` / `0.75` / `0.85`) | 5 / 4 / 3 |

Посчитать свою модель:

```bash
uv run python -c "import json; from loom.orchestrator.broker import ResourceBroker; from loom.orchestrator.registry import ModelSpec; s=ModelSpec.from_dict(json.load(open('configs/catalog-qwen3-32b-shard.json'))['models'][0]); b=ResourceBroker(param_mem_ratio=0.75); print('слоёв на карту 24GB:', b.layers_fitting(24*1024**3, s.model_info), 'из', s.model_info.num_layers)"
```

**Запуск.** Каталог `configs/catalog-qwen3-32b-shard.json` уже готов:

```bash
LOOM_CATALOG=catalog-qwen3-32b-shard.json LOOM_PARAM_MEM_RATIO=0.75 LOOM_PUBLIC_ADDR=<host>:9000 LOOM_ADMIN_TOKEN=<token> LOOM_PG_PASSWORD=<pw> docker compose -f docker-compose.prod.yml up -d --build
```

Дальше подключаете N GPU-машин обычной командой с ключом (§4). Как только их
суммарной ёмкости хватит, Phase-1 сам разложит слои, а оркестратор разошлёт
стадиям их диапазоны. Проверить раскладку:

```bash
curl -s localhost:8000/admin/models_view -H "X-Loom-Admin-Token: $LOOM_ADMIN_TOKEN" | python3 -m json.tool
```

В `placement` увидите по строке на стадию: `node`, `layers`, `status`.
Клиентский эндпоинт будет ровно один — у головы (стадия 0); запросы шлются как
обычно на `/v1/chat/completions`.

**Что важно знать про многостадийный режим:**

- **Каждый узел скачивает весь чекпойнт**, хотя грузит в память только свои
  слои (для 32B это ~61 GB загрузки на каждую машину). Смонтируйте общий кеш
  (`-v loom-hf:/root/.cache/huggingface`) и, если машины в одной сети, заранее
  прогрейте кеш или раздайте веса локальным зеркалом. Постадийная выборка
  файлов — оптимизация на будущее.
- **Латентность на токен растёт с числом стадий**: активации идут
  `стадия → оркестратор → следующая стадия`, а токен возвращается на голову.
  Грубая оценка: `≈ 2 × RTT(воркер↔оркестратор)` на каждый переход. Держите
  узлы и оркестратор в одном регионе; 100 мс RTT — это уже единицы токенов в
  секунду.
- **Скорость ниже, чем у vLLM**: shard-исполнитель на transformers, без paged
  attention и continuous batching, одна последовательность на запрос. Для
  моделей, влезающих на одну карту, оставляйте `"backend_type": "vllm"` — он
  быстрее. `shard` нужен именно там, где модель не влезает.
- **Одна карта на узел**: шард-процесс использует `cuda:0`. На многокарточной
  машине запускайте по контейнеру на карту:
  `--gpus '"device=0"' -e LOOM_NODE_ID=box1-gpu0`, `--gpus '"device=1"' -e LOOM_NODE_ID=box1-gpu1` и т.д.
  Каждый такой контейнер — отдельный узел пула, и Phase-1 может поставить на
  них разные стадии.
- **Потеря любой стадии рвёт пайплайн**: оркестратор увидит отключение,
  снимет эндпоинт и переразложит модель на оставшихся узлах (если хватает
  ёмкости). Реплики (`target_pipelines > 1`) дают устойчивость: каждая реплика
  независима.

## 7. Ограничения, которые надо знать до тестов

- **Модель должна влезать на один узел.** Phase-1 умеет резать модель между
  узлами, но передачи активаций между стадиями пока нет, поэтому прод-адаптеры
  (vLLM/SGLang/MLX) принимают только полный диапазон слоёв. Реплики
  масштабируются «в ширину»: k реплик = k узлов.
- **Число реплик** задаётся в каталоге (`target_pipelines` или
  `demand_qps`/`LOOM_QPS_PER_PIPELINE`), а не числом подключённых машин.
  Лишние узлы просто ждут (sticky-политика брокера).
- **Транспорт без TLS.** gRPC поднят как insecure: до выхода в открытый
  интернет закройте 9000 фаерволом/VPN или поставьте TLS-терминацию.
  mTLS — следующий шаг по безопасности.
- **Первый запуск vLLM долгий** (скачивание весов + прогрев). Пока бэкенд не
  ответил на health, узел в `/admin/nodes` показывает шард в статусе
  `loading`; API на эту модель отдаёт 503.
- **Цена узла** пока не собирается (поле `price: null`) — это Фаза 4
  (онбординг с декларацией цены, калибровка, биллинг).

## 8. Диагностика

| Симптом | Куда смотреть |
|---|---|
| Узел не появился | логи воркера (`docker logs loom-worker`): «invalid join key» / нет сети до `LOOM_PUBLIC_ADDR` |
| Узел есть, `tunnel: false` | воркер не смог открыть второй стрим — тот же порт 9000, проверьте прокси/фаервол |
| Модель `unscheduled` | `docker compose logs orchestrator \| grep Broker` — не хватает VRAM: поднимите `LOOM_PARAM_MEM_RATIO` или возьмите модель меньше |
| 503 на запрос | шард ещё `loading` (качается модель) либо бэкенд упал — `/admin/nodes`, затем логи воркера |
| 502 «worker unreachable» | туннель порвался; воркер переподключится сам, запрос можно повторить |
| Бэкенд убит | watchdog при превышении квоты: `docker logs loom-worker \| grep watchdog`; оркестратор передеплоит модель сам |

Дашборд для ручных проверок: **`/admin/ui`** — узлы с автодетектом и статусами
шардов, каталог с раскладкой, τ/ρ Perf-map, SLO, выдача ключей, тестовая
консоль запросов.
