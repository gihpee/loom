# Развёртывание

Что поднять, в каком порядке, и что проверить прежде чем звать владельцев
машин. Архитектура — [ARCHITECTURE.md](ARCHITECTURE.md); подробно про узлы —
[AGENT_MANUAL.md](AGENT_MANUAL.md).

---

## 1. Оркестратор

Нужна машина с публичным адресом — единственная во всей системе.

```bash
bash scripts/init_env.sh          # создаёт .env и генерирует админ-токен
docker compose up -d --build
```

Проверить, что он определил свой адрес правильно:

```bash
curl -s localhost:8000/admin/connect -H "X-Looma-Admin-Token: $LOOMA_ADMIN_TOKEN"
```

`severity: "warn"` означает, что до объявленного адреса не достучаться снаружи,
и **ни один узел не подключится**. Обычно лечится явным `LOOMA_PUBLIC_ADDR` в
`.env`: автоопределение видит адрес контейнера, а не то, что видно из мира.

Порт `LOOMA_GRPC_PORT` должен быть открыт наружу. Это единственный входящий порт
во всей системе — у узлов их нет вовсе.

Пересобирать оркестратор можно под нагрузкой: `docker compose up -d --build` не
трогает узлы, их задачи продолжают считать, а оркестратор поднимается со своим
состоянием из тома `looma-data` (`/data/state.json`) — развёрнутые модели и
задачи остаются на месте. Оттуда же он берёт ключи и релизы, так что
`docker compose down -v` стирает и их: том сносят, только когда хотят начать
с чистого листа.

## 2. Ключ и узел

Ключ выдаётся в панели (`http://<оркестратор>:8080`, вкладка Keys) или запросом:

```bash
curl -s localhost:8000/admin/keys -X POST \
  -H "X-Looma-Admin-Token: $LOOMA_ADMIN_TOKEN" \
  -H 'Content-Type: application/json' -d '{"label":"машина Миши"}'
```

Ответ содержит готовую команду. Владелец выполняет **одну строку**:

```bash
docker run -d --gpus all --restart unless-stopped --network host \
  -v looma-data:/var/lib/looma gihpee/looma-agent --key looma_...
```

Три вещи в ней не косметика:

`--network host` — без него p2p-порт остаётся внутри контейнера, и прямой
канал между узлами невозможен: порт контейнера не порт хоста, а исходящие
пакеты транслируются ещё раз на выходе. Пробивание NAT из такой позиции не
работает никогда.

`-v looma-data:/var/lib/looma` — сюда ложатся каталоги задач, кэш окружений и
нагрузки агента. Без тома всё это пересобирается заново после каждого
перезапуска, и обновление агента не переживает рестарт.

`--restart unless-stopped` — иначе узел исчезает после первой же перезагрузки
машины, и владелец об этом не узнает.

Через несколько секунд узел виден в админке на вкладке Nodes.

## 3. Что узел скажет о себе сам

В его логе при старте есть строка о железе и строка о готовности:

```
hardware: device=cuda gpu=NVIDIA GeForce RTX 4090 x2 vram_free=47.3GB ... (nvml)
tasks will run as looma-task on 2 GPU(s)
```

Если вместо второй строки:

```
this node will REFUSE every task until it can run them as a separate user
```

— значит агент запущен не от root либо в образе нет пользователя `looma-task`.
Узел при этом **зарегистрируется и будет виден**, но не возьмёт ни одной
задачи. Это намеренно: запускать чужой код от пользователя агента — значит
отдать ему ключ узла и файлы соседних задач.

## 4. Реле (необязательно)

Нужно только тем узлам, до которых не дозванивается даже другой узел. Без него
такой узел возит всё через оркестратор: правильно, и вдвое больше дальних
переходов.

```bash
docker compose up -d relay
```

Порт `47200` должен быть открыт. Адрес реле публикуется в
`/data/relay/address`, откуда оркестратор его и берёт — прописывать руками
ничего не надо. Подробности и диагностика: [P2P_RELAY.md](P2P_RELAY.md).

## 5. Развернуть модель

Модель — это группа задач: стадии, размещённые вместе или не размещённые
вовсе. Каждой стадии свой диапазон слоёв, потому что разрез решает
оркестратор — только он знает, что каждый узел выдержит.

```bash
curl -s localhost:8000/admin/groups -X POST \
  -H "X-Looma-Admin-Token: $LOOMA_ADMIN_TOKEN" \
  -H 'Content-Type: application/json' -d '{
    "label": "qwen3-8b",
    "size": 2,
    "serve_port": 1,
    "timeout_s": 0,
    "environment": {"kind": "python", "requirements": ["looma-stage"]},
    "per_rank": [
      {"command": ["python","-m","looma_stage.server","--model-id","qwen3-8b",
                   "--weights-uri","Qwen/Qwen3-8B","--start-layer","0","--end-layer","18",
                   "--device","cuda","--dtype","bfloat16"]},
      {"command": ["python","-m","looma_stage.server","--model-id","qwen3-8b",
                   "--weights-uri","Qwen/Qwen3-8B","--start-layer","18","--end-layer","36",
                   "--device","cuda","--dtype","bfloat16"]}
    ]}'
```

`label` — то имя, которым модель спрашивают клиенты. `serve_port: 1` означает
«обслуживай, и скажи на каком порту»: номер выбирает сама стадия, потому что
между предложением и занятием порт может занять кто-то ещё — а на многокарточном
хосте два агента живут на одной машине.

Первый запуск на узле долгий: качаются веса и ставится окружение. Второй —
мгновенный, окружение кэшируется.

Проверить:

```bash
curl -s localhost:8000/v1/models
curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"qwen3-8b","messages":[{"role":"user","content":"привет"}]}'
```

## 6. Обновить агентов

Ключ подписи создаётся один раз и **не кладётся на оркестратор**:

```bash
uv run --with cryptography python scripts/sign_release.py keygen --out agent-release.key
scripts/build_agent.sh --push        # образ с публичной половиной ключа внутри
```

Дальше каждый релиз:

```bash
uv run --with cryptography python scripts/sign_release.py \
  sign --key agent-release.key --version 0.3.0
```

Команда печатает подпись и готовый `curl` для публикации. Публикация **не
начинает выкатку** — ступень переводится руками в панели, на вкладке Release.
Почему не автоматически: [WORKER_UPDATE.md](WORKER_UPDATE.md).

## 7. Когда что-то не так

| симптом | что смотреть |
|---|---|
| узел не появляется | `/admin/connect` — `severity` и `self_check`; порт GRPC снаружи |
| узел есть, задачи не берёт | лог агента при старте: почему отказывается |
| задача падает сразу | `/admin/tasks/<id>/logs` — там stdout самой задачи |
| всё идёт через оркестратор | лог агента: он называет причину, по которой прямой путь невозможен |
| нода пропала после перезапуска оркестратора | должна вернуться за секунды; если нет — keepalive не доходит, смотреть туннель/NAT между ними |
