# Прямой канал между воркерами

Единый документ по p2p-транспорту Loom: зачем, как устроено, что уже сделано,
что дальше и что проверено вживую.

Опорная работа: **Lattica: A Decentralized Cross-NAT Communication Framework
for Scalable AI Inference and Training** (Gradient, arXiv:2510.00183v2). Из неё
взята архитектура; реализация — наша, потому что у Loom есть то, чего у чистой
p2p-сети нет: **доверенный координатор**.

---

## 1. Зачем

Замер на трёх географически разнесённых нодах:

```
компьют всех стадий: 50.0 ms  (38% токена)
транспорт:           80.4 ms  (60%)
между токенами:      p50 132.9 ms / p95 349.4 ms
```

Транспорт съедает больше, чем сами вычисления. Причина структурная: каждый
прыжок между стадиями идёт **через оркестратор**, то есть пересекает сеть
дважды. Три стадии — это три прыжка (`0→1`, `1→2`, возврат токена `2→0`) и
**шесть пересечений WAN** на токен, по ~13.4 ms каждое.

Прямые связи убирают половину:

| | сейчас | напрямую |
|---|---|---|
| пересечений WAN на токен | 6 | 3 |
| транспорт | 80.4 ms | ~40 ms |
| между токенами | 132.9 ms | ~90 ms |
| **tok/s** | **7.5** | **~11.1** |
| трафик на токен | 96 КБ | 48 КБ |

Оценка получена делением пополам числа пересечений и потому консервативна: если
оркестратор географически дальше от пары нод, чем они друг от друга, выигрыш
будет больше.

---

## 2. Главное архитектурное решение

**Оркестратор остаётся единственным доверенным узлом.** Мы не строим
децентрализованную сеть — мы добавляем второй, недоверенный путь для объёмных
данных.

| | контрольный канал | канал данных |
|---|---|---|
| что ходит | LoadShard, StartServing, телеметрия, ключи | активации, токены |
| через кого | оркестратор (hub-and-spoke) | напрямую между воркерами |
| доверие | аутентификация по join-ключу, HMAC-подпись команд | нет, это чужие байты |
| если сломалось | воркер переподключается | падаем на релей оркестратора |

Оркестратор в прямом пути **не участвует**. Он даёт три факта, которых воркер
не может получить сам, и уходит:

1. **Кто соседи.** Раскладку решает он, значит только он знает, что стадия 2
   переехала на другую машину.
2. **Какой у ноды публичный адрес.** Машина за NAT видит только свой приватный
   адрес. Оркестратор видит адрес, с которого пришло управляющее соединение —
   это и есть публичный адрес ноды, тот самый факт, ради которого существует
   STUN. Мы получаем его бесплатно из соединения, которое воркер и так открыл.
3. **Стоит ли вообще пытаться.** Нода за симметричным NAT пробиванию не
   поддаётся; сообщить об этом заранее дешевле, чем дать каждому соседу
   выяснить это таймаутом.

### Чего здесь сознательно нет

**DHT для обнаружения.** В Lattica распределённая хеш-таблица нужна потому, что
координатора нет в принципе. У нас он есть и уже знает ответ — поиск в DHT был
бы медленнее, слабее и бессмысленнее. libp2p используется ровно для того, в чём
он незаменим: **свести две машины за NAT**.

## 3. Как это работает

### 3.1. Личность вместо адреса

Нода в libp2p — это `peer_id` вида `12D3KooWQTKdknCb...`, хеш её публичного
ключа. Не IP, не домен: **криптографическая личность**. Машина может сменить
сеть, провайдера, IP — она останется тем же пиром, и вы точно знаете, с кем
говорите.

Адрес пишется как multiaddr — протокол зашит прямо в строку:

```
/ip4/10.0.0.5/tcp/47100                 — TCP
/ip4/10.0.0.5/udp/47100/quic-v1         — QUIC
/ip4/203.0.113.7/tcp/47100/p2p/12D3KooW…  — с указанием, кто там должен быть
```

Одна нода анонсирует несколько адресов: сосед пробует их по порядку.

### 3.2. Rendezvous: как пиры находят друг друга

Это ключевой механизм, и он проверен экспериментом (§7).

Оркестратор поднимает свой узел Lattica и раздаёт его multiaddr всем воркерам.
Каждый воркер при старте подключается **только к нему**. После этого воркер
может обратиться к любому другому **по одному лишь `peer_id`** — стек сам
находит его через общий rendezvous и устанавливает соединение.

```
        воркер A ──┐                 ┌── воркер B
                   ├── rendezvous ───┤        только для знакомства
        воркер C ──┘  (оркестратор)  └── воркер D

        A ══════════════════════════════ B   активации идут напрямую
```

Важное следствие: **воркеру не нужно знать адрес соседа**. Достаточно `peer_id`.
Это и делает схему работоспособной для машин за NAT, которые своего адреса не
знают и анонсировать не могут.

### 3.3. Пробивание NAT

Прямое соединение между двумя машинами за NAT устанавливается так:

1. **AutoNAT** — нода выясняет, доступна ли она снаружи вообще.
2. **Relay** — если нет, соединение сперва идёт через ретранслятор (у нас это
   узел оркестратора). Работает всегда.
3. **DCUtR** (Direct Connection Upgrade through Relay) — по установленному
   relay-каналу пиры синхронизируют время и **одновременно** бьют пакетами
   навстречу. Каждый NAT записывает в свою таблицу «наш узел общается с тем
   адресом», и следующий пакет с другой стороны уже проходит. Соединение
   «схлопывается» в прямое.

По данным статьи Lattica, hole punching даёт **около 70% успеха**; остальные
30% остаются на relay. Это не недостаток реализации, а свойство сетей:
симметричный NAT выдаёт новый порт на каждого собеседника, поэтому адрес, по
которому сосед стучится, заведомо не тот.

**Поэтому релей никуда не девается.** 30% пар будут работать через
оркестратор — так же, как сейчас работают 100%.

### 3.4. Выбор пути на каждом сообщении

```
стадия ──POST──> релей агента ──> [LinkTable] ──┬── прямо к пиру
  (не знает, каким путём)                       └── туннель оркестратора
```

Правило намеренно скучное: **есть живой прямой путь — идём им, нет — релеем,
и никогда не теряем токен**. Пайплайн, который молча ушёл на релей, просто
медленнее; пайплайн, потерявший сообщение, сломан.

Упавший прямой линк уходит в «карантин» на 30 секунд: повтор на каждом токене
добавлял бы таймаут к каждому токену.

Широковещательные сообщения (`FREE`, освобождение KV на всех стадиях) идут
через релей **сознательно** — они крошечные, редкие, вне критического пути, и
релей уже умеет разослать их всему пайплайну одним сообщением.

## 4. Что изменилось в коде

### Протокол

`gateway.proto` — новое сообщение `PeerIdentity` в `RegisterRequest`:

```protobuf
message PeerIdentity {
  string peer_id = 1;              // 12D3KooW…
  repeated string listen_addrs = 2; // кандидаты, не истина
  bool symmetric_nat = 3;           // пробивать бесполезно
}
```

`worker_control.proto` — адресная книга в `PipelineTopology`:

```protobuf
message PeerRoute {
  int32 stage_index = 1;
  string node_id = 2;
  string peer_id = 3;      // пусто = только релей
  repeated string addrs = 4;
}
```

Оба поля необязательные: воркер без p2p-стека и оркестратор старой версии
продолжают работать как раньше.

### Оркестратор

| файл | что |
|---|---|
| `orchestrator/peers.py` | **новый.** `PeerDirectory` — кто где, порядок кандидатов, кого нельзя дозвонить |
| `orchestrator/gateway.py` | `_observed_host()` — публичный адрес из gRPC-соединения (бесплатный STUN) |
| `orchestrator/controller.py` | `self.peers`, `_peer_routes()` — книга кладётся в топологию при каждом развёртывании |

### Воркер

| файл | что |
|---|---|
| `p2p/peer.py` | **новый.** `PeerNode` — обёртка над Lattica: личность, вход в сеть, входящий RPC |
| `p2p/links.py` | **новый.** `LinkTable` — выбор пути, карантин, фолбэк, статистика |
| `dataplane_client.py` | `_on_stage_outgoing` спрашивает `LinkTable`; `deliver_direct` принимает прямые сообщения |
| `handlers.py` | применяет адресную книгу из `LoadShard` |
| `main.py` | `start_peer_layer()` — поднять узел или спокойно жить без него |

**Шов оказался ровно там, где и предполагалось.** Процесс стадии не тронут ни
одной строкой: он по-прежнему POST-ит сообщение на локальный релей агента и
ничего не знает о том, каким путём оно уйдёт.

### Переключатели

| переменная | по умолчанию | зачем |
|---|---|---|
| `LOOM_P2P` | `1` | `0` полностью выключает прямой путь |
| `LOOM_P2P_PORT` | `47100` | TCP и QUIC на одном номере |
| `LOOM_P2P_KEY_DIR` | `/root/.cache/loom/p2p` | ключ + состояние узла; **у каждой ноды свой** |
| `LOOM_P2P_RENDEZVOUS` | пусто | multiaddr узла оркестратора. **Пусто = p2p не поднимается вовсе** |

Последняя строка не оговорка. Без rendezvous узел никем не может быть найден
(bootstrap-пиры фиксируются при сборке, §5), и заявить о себе как о достижимом
означало бы подарить каждому соседу один провальный вызов и 30 секунд
карантина. Пока фаза 2 не сделана, воркер честно работает через релей.

## 5. Что проверено вживую

Не по документации, а запуском настоящих узлов Lattica (`lattica==1.0.21`,
abi3-колёса под linux x86_64/aarch64, macOS, Windows, ~10 МБ):

| проверка | результат |
|---|---|
| ядро стартует, выдаёт `peer_id` | ✅ `12D3KooW…` |
| два узла соединяются по прямому адресу | ✅ за 0.25 с |
| **два узла находят друг друга, зная только rendezvous** | ✅ **3 из 3, ~105 мс на первый вызов** |
| RPC с полезной нагрузкой 16 КБ (активация Qwen3-8B) | ✅ 0.91 мс/вызов на петле |
| `get_peer_rtt` даёт измеренный RTT | ✅ 0.107 мс на петле |
| личность переживает перезапуск (`with_key_path`) | ✅ |
| dict с `bytes` внутри переживает сериализацию | ✅ |

### Три находки, стоившие отладки

**`with_bootstraps` после `build()` не работает.** Bootstrap-пиры фиксируются
при сборке узла. Отсюда и вся схема с rendezvous: нельзя «дозвониться по
адресу» позже, можно только войти в сеть через известную точку и дальше искать
по `peer_id`. Метод `PeerNode.warm()` честно называется «прогреть», а не
«дозвониться».

**`get_all_peers()` — не признак готовности к конкретному пиру.** Он
перечисляет уже установленные соединения. Подключение к rendezvous **не**
связывает двух воркеров между собой: сосед резолвится в момент первой отправки.
Первый вызов стоит ~100 мс, дальше субмиллисекунды. Ждать «появления пира в
списке» бессмысленно — надо просто слать.

**Узлу нужно время войти в сеть.** `build()` возвращается мгновенно, но пока
узел не присоединился к rendezvous, любая отправка падает с «failed to
reconnect». Поэтому `start()` дожидается входа (`JOIN_TIMEOUT_S = 15 s`) — иначе
первые токены каждого развёртывания уходили бы на релей без причины.

Плюс тестовая мелочь с производственным следом: **закрытый узел освобождает порт
не мгновенно**, и каждой ноде нужен собственный `key_dir` — Lattica держит там
не только ключ.

**Почему не «ленивый старт при первом `LoadShard`».** Вход в сеть занимает
секунды, и развёртывание не должно быть тем, кто их ждёт. К моменту прихода
`LoadShard` узел уже в сети, и первые токены идут напрямую, а не откатываются
на релей «пока подключаемся».

**Почему личность едет в heartbeat, а не только в регистрации.** Воркер узнаёт
адрес rendezvous **из ack** — то есть в момент регистрации у него ещё нет
`peer_id`. Побочная выгода: оркестратор после перезапуска восстанавливает всю
адресную книгу за один удар сердца, ровно как восстанавливает список шардов.

### Формат провода: bf16 вместо float32 ✅ *сделано*

Активации поднимались до float32 «ради переносимости» — чтобы стадия на CPU
(float32) и стадия на GPU (bfloat16) понимали друг друга. Но переносимость даёт
не общий формат, а то, что **dtype едет вместе с тензором**, и он ехал всегда.
На bf16-модели этот апкаст удваивал каждый байт, не добавляя ни бита: принимающая
стадия тут же сужала обратно, чтобы считать.

Правило теперь в одну строку: **никогда не расширять тензор ради отправки.**
Сужать по своей инициативе тоже нельзя — стадия на CPU действительно считает в
float32, и её выход потерял бы разряды. Поэтому по умолчанию едет собственный
dtype тензора, а `LOOM_WIRE_DTYPE` (`auto` | `bfloat16` | `float16` |
`float32`) позволяет закрепить формат — для замеров и для пайплайна, стадии
которого разошлись.

Что это даёт на замере с тремя стадиями (hidden 4096):

| | на сообщение | на токен | полоса на один запрос |
|---|---|---|---|
| было: релей + float32 | 16 КБ | 96 КБ | 5.92 Мбит/с |
| p2p + float32 | 16 КБ | 48 КБ | 2.96 Мбит/с |
| релей + bf16 | 8 КБ | 48 КБ | 2.96 Мбит/с |
| **p2p + bf16 (сейчас)** | **8 КБ** | **24 КБ** | **1.48 Мбит/с** |

Вчетверо меньше трафика за те же токены. На локалке это почти не заметно, на
WAN байты — это время.

**Неизвестный dtype теперь отвергается, а не угадывается.** Раньше обе стороны
при незнакомом имени молча читали как float32. Прочитать байты bf16 как float32
не падает — получаются числа, вдвое меньше числом, и все неверные, а пайплайн
на них отвечает бегло, уверенно и неправильно. Это тот же класс отказа, что мы
уже ловили с испорченным KV, и единственный способ до него добраться —
разные образы воркера в одном пайплайне, о чём текст ошибки прямо и говорит.

Обе реализации (`shard` и `vllm_shard`) теперь ходят через `loom_worker/wire.py`
и потому совместимы между собой — это отдельно закреплено тестом.

## 7. Что выяснилось на фазе 2

Три вещи, найденные экспериментом, а не чтением документации.

### `with_relay_servers` оставляет узел вне сети

Указание нашего rendezvous как relay-сервера **ломает подключение целиком**:
узел ждёт резервацию circuit-relay, которой ему никто не даст, и остаётся с
нулём пиров.

```
relay_servers=True :  0 пиров за 15092 ms
relay_servers=False:  1 пир  за   112 ms
```

Причина: relay в libp2p — это **служба**, которую сторона-ретранслятор должна
предоставлять явно. У Parallax под это выделены отдельные хосты
(`relay-lattica-*.gradient.network`); наш rendezvous — точка входа в DHT, а не
ретранслятор. В API Lattica включателя relay-службы нет вовсе.

**И он нам не нужен.** У Loom уже есть релей — туннель оркестратора, через
который сегодня идёт весь трафик: собранный, аутентифицированный, рабочий.
Circuit relay был бы вторым, избыточным.

**Следствие, которое надо знать честно:** DCUtR пробивает NAT, координируясь по
уже установленному relay-соединению. Без libp2p-relay пара, где **обе** стороны
за NAT, прямой канал не построит — она уйдёт на наш туннель. Прямо соединятся
пары, где хотя бы одна сторона доступна снаружи (арендованный сервер с белым
IP — как раз этот случай) или обе в одной локалке. Для вашего стенда это
работает; для домашних GPU в маркетплейсе — часть пар останется на релее, и
превратить rendezvous в настоящий relay-сервер придётся отдельной задачей.

### UPnP включён

`with_upnp(True)` просит роутер пробросить порт. Бесплатно, когда срабатывает
(многие домашние роутеры умеют), молча, когда нет. Каждая нода, ставшая
доступной снаружи, — это ещё одна пара, которая соединится напрямую.

### Каталог ключей — строго свой на узел

Lattica держит в `with_key_path` не только ключ. Два узла, указавшие один
каталог, мешают друг другу и не находят пиров. В продакшене это само собой
(контейнер на ноду), но `PeerLayer` принимает `port`/`key_dir` явно — иначе
несколько агентов в одном процессе не поднять.

### Маршруты принадлежат пайплайну, а не ноде

Нашлось при разборе вопроса «что будет при переразвёртывании». Нода может
держать стадии **нескольких моделей одновременно**, и «стадия 1» — это разная
машина в каждой из них.

Две проблемы, одна из которых была и до p2p:

1. **Стадия не сообщала свой `pipeline_id`.** Агент угадывал его как «первый
   многостадийный шард, который я хостю». С одной моделью на ноде — верно,
   с двумя — лотерея, причём и на релейном пути тоже. Теперь стадия
   проставляет `pipeline_id` и `model_id` сама: она единственная, кто знает их
   точно. Старый способ остался только для стадии из старого образа и теперь
   пишет предупреждение, если моделей больше одной.
2. **`LinkTable` ключевалась по индексу стадии.** Развёртывание второй модели
   затирало соседей первой, а сообщение могло уехать на ноду чужого пайплайна.
   Теперь ключ — `(pipeline_id, stage_index)`, и `set_neighbours` заменяет
   строки **только своего** пайплайна.

Тип отказа тут особенно неприятный: принимающая стадия честно прогоняет свои
слои по любому пришедшему тензору, поэтому получился бы не сбой, а правдоподобно
выглядящий неверный ответ.

## 8. Как включить

Оркестратору нужен **открытый порт** — TCP и UDP, по умолчанию 47100, вдобавок
к gRPC. Это единственный хост в системе, которому нужен входящий доступ;
воркерам по-прежнему открывать ничего не надо.

```yaml
# docker-compose.prod.yml, сервис orchestrator
ports:
  - "47100:47100/tcp"
  - "47100:47100/udp"
```

Дальше ничего настраивать не надо: оркестратор поднимет rendezvous, объявит
себя по своему публичному адресу (тому же, что уже раздаётся в join-ключах) и
раздаст multiaddr воркерам в ack. В логе будет:

```
rendezvous up: 12D3KooW… on port 47100 — workers will be told to bootstrap here
rendezvous multiaddrs: /ip4/…/tcp/47100/p2p/12D3KooW…, /ip4/…/udp/47100/quic-v1/p2p/…
```

На воркере — `direct path enabled` и дальше в админке, вкладка **Nodes**,
колонка `p2p`: `peer · 100% прямо · 244/244`. Если там `relay` — значит прямой
путь не поднялся, и это видно сразу, а не по загадочной латентности.

Выключается на любой стороне: `LOOM_P2P=0`.

| переменная | где | по умолчанию |
|---|---|---|
| `LOOM_P2P` | оба | `1` |
| `LOOM_P2P_PORT` | оба | `47100` |
| `LOOM_P2P_KEY_DIR` | воркер / оркестратор | `/root/.cache/loom/p2p` / `/data/p2p` |

## 9. Потолок, который транспорт не уберёт

Одна последовательность на конвейере из N стадий требует **N сетевых прыжков на
токен**. Это причинность, а не реализация: стадия 1 не может начать, пока не
пришёл результат стадии 0.

Три стадии по 13 ms в один конец = 40 ms на токен **при идеальном p2p, нулевом
компьюте и бесконечной полосе** — потолок 25 tok/s. Разнесите ноды по
континентам с RTT 150 ms, и потолок станет 6.6 tok/s, хоть H100 туда ставьте.

Прямой канал сокращает **цену** прыжка вдвое. Число прыжков сокращает
раскладка (меньше стадий). А **перестать ждать каждый прыжок** умеют только
спекулятивное декодирование и пакетирование — они в фазе 4, и без них
межконтинентальный одиночный запрос быстрым не станет никогда.
