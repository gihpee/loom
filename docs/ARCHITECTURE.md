# Архитектура Looma

Документ для человека, который открыл репозиторий впервые. Устройство узла
изнутри — [WORKER_RUNTIME.md](WORKER_RUNTIME.md); здесь про то, как части
складываются в систему.

---

## 1. Задача, из которой всё следует

Сдать в аренду можно только ту машину, которую легко подключить. Домашний
компьютер за роутером провайдера **недозвоним**: у него нет публичного адреса,
он не будет открывать порты, и его владелец не станет настраивать проброс.

Поэтому в Looma **никто никогда не звонит узлу**. Узел звонит сам, один раз, и
держит соединение. Всё остальное — команды, файлы, результаты, активации
инференса — едет внутри него.

Отсюда же и главное отличие от площадок вроде vast.ai, где хост обязан быть
дозвонимым: там это отсекает домашние машины, а здесь они и есть аудитория.

## 2. Четыре части

```
       клиент
         │  /v1/chat/completions
         ▼
 ┌──────────────────┐
 │   ОРКЕСТРАТОР    │  кто чем занят, кому какая работа, кому какой релиз
 └────────┬─────────┘
          │  один gRPC-стрим на узел, открытый узлом
   ┌──────┴───────────────────────┐
   ▼                              ▼
┌────────┐                    ┌────────┐
│ АГЕНТ  │◄── прямой канал ──►│ АГЕНТ  │   p2p, когда возможно
│        │      (p2p)         │        │
│ задача │                    │ задача │   ← НАГРУЗКА: стадия модели,
└────────┘                    └────────┘     обучение, код клиента
```

**Оркестратор** (`src/looma/`) решает и учитывает. Он не считает и не хранит
моделей.

**Агент** (`agent/`) стоит на чужой машине. Тоже не считает: он принимает
команду, разворачивает под задачу каталог, наполняет его нужным окружением и
запускает там процесс.

**Нагрузка** (`payloads/`) — то, что считает. Стадия модели ставится в задачу
тогда, когда просят инференс, и отсутствует на узле, которого не просили.
Поэтому образ агента маленький: в нём нет ни torch, ни vLLM.

**Реле** (`relay/`) нужно узлам, до которых не дозванивается даже другой узел.
Необязательно: без него такой узел просто возит всё через оркестратор.

## 3. Как узел подключается

```
владелец: docker run ... --key looma_...
    │
    │  в ключе адрес оркестратора и секрет — больше владелец не вводит ничего
    ▼
агент дозванивается, открывает стрим Attach
    │
    ├─→ Register: железо (определено, не заявлено) + готовность брать работу
    │
    └─← RegisterAck: адрес rendezvous для p2p, адрес реле,
                     и какую версию агента этот узел должен запустить
```

Регистрация — первое сообщение в стриме **всегда**, поэтому переподключение
не требует отдельной логики: узел просто представляется заново.

## 4. Как выполняется работа

```
оркестратор                     агент                         задача
    │  RunTask ───────────────────→│
    │                              │ 1. каталог tasks/<id>/{work,out}
    │  InputChunk ────────────────→│ 2. файлы клиента в work/
    │                              │ 3. окружение: из кэша или ставится
    │                              │ 4. запуск ──────────────────→ процесс
    │  ← TaskState (running) ──────│                                 │
    │                              │ ← stdout ───────────────────────│
    │  ← TaskState (done, файлы) ──│ ← файлы в out/ ─────────────────│
    │  FetchResult ───────────────→│
    │  ← ResultChunk ──────────────│
```

Ничего медленного не происходит на потоке стрима: установка окружения может
идти полчаса, и узел, переставший читать стрим, выглядел бы мёртвым.

## 5. Как работает инференс

Модель не влезает в одну карту — её режут по слоям между узлами. Стадии
образуют **группу**: задачи, размещённые вместе или не размещённые вовсе.

```
клиент → оркестратор → ранг 0 ──активации──→ ранг 1 ──→ ранг 2
                          ▲                                │
                          └──────────── токен ─────────────┘
```

Стадия шлёт **рангу**, а не адресу. Где этот ранг живёт — та же машина,
сосед по прямому каналу, или дальняя сторона оркестратора — решает агент.
Задача, знающая про соседей, вынуждена была бы знать про NAT и реле.

Три пути, по убыванию стоимости:

| путь | когда | цена |
|---|---|---|
| та же машина | обе стадии на одном узле | нет сети вообще |
| прямой p2p | хотя бы одна сторона дозвонима | один переход |
| через оркестратор | иначе | два дальних перехода |

Правило выбора **топологическое, а не по замерам**: см.
[P2P_TRANSPORT.md](P2P_TRANSPORT.md), там же почему.

## 6. Как обновляется парк

Образ агента почти не меняется — в нём только пусковой слой. Сам агент
приезжает **подписанной нагрузкой**, которую пусковой слой проверяет и
устанавливает.

Оркестратор не пушит обновление, а **объявляет желаемую версию**; узлы к ней
сходятся. Поэтому узел, выключенный неделю, догоняет сам, а новый приходит
сразу правильным.

Ключ подписи у оркестратора отсутствует намеренно: его захват должен
позволять назвать любой из уже подписанных релизов — плохо, — но не запустить
новый код на каждой машине парка. Подробности: [WORKER_UPDATE.md](WORKER_UPDATE.md).

---

## 7. Что защищено, а что нет

**Владельца машины защитить можно**, и это сделано: задача исполняется от
отдельного пользователя, в своём каталоге, с лимитами памяти, процессов и
диска, снимается по таймауту вместе со всем деревом процессов, и не видит
окружения агента — где лежит ключ узла.

**Клиента от владельца машины защитить нельзя.** У владельца root на его
машине: он может прочитать память процесса, посмотреть, что на карте, и
подменить результат. Помогло бы конфиденциальное исполнение на уровне железа,
которого на потребительских картах нет. Работа, чья ценность — сами данные
или веса, на такой парк отдаваться не должна.
