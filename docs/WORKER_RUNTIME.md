# Целевая архитектура воркера

> **Статус: реализовано.** Так узел и устроен. Раздел «Чем это отличается от
> сегодняшнего» оставлен как запись того, что изменилось по сравнению со
> старой архитектурой, которой в репозитории больше нет.

---

## 1. Три решения, из которых следует всё остальное

**Воркер — контейнер.** Не обсуждается. Одна команда на машине владельца, без
установки чего-либо на хост, без настройки сети, без root.

**Образ тонкий.** В нём только агент: связь с оркестратором, p2p, отчёт о
существовании. Ни vLLM, ни torch, ни чего-либо ещё. Инференс — такая же
задача, как остальные, и воркер не обязан его уметь, если оркестратор не
просит.

**Всё, что считает, живёт в каталоге задачи.** Оркестратор говорит, какая
задача; агент разворачивает под неё каталог, наполняет его нужной средой,
исполняет там и отдаёт результат наружу. Инференс, обучение и клиентские
вычисления — три случая одного механизма.

Из третьего пункта прямо следует, чего в схеме **нет**: докер-сокета,
вложенного демона, привилегированного контейнера. Ничего из этого не нужно,
потому что задача не запускает контейнер — она разворачивается в каталоге.

---

## 2. Образ

Два варианта, владелец выбирает при подключении:

| образ | что внутри | для кого |
|---|---|---|
| `loomworker:base` | Python + агент + p2p | всё, что ставится колёсами |
| `loomworker:cuda` | то же + CUDA-рантайм | то, что собирается из исходников |

Тонкой хватает даже для работы на карте: колёса PyTorch везут свою CUDA-часть
пакетами `nvidia-*`, поэтому достаточно драйвера на хосте и `--gpus all`.
CUDA-вариант нужен там, где какая-то зависимость требует `nvcc` при установке.

По умолчанию — тонкая.

---

## 3. Каталоги

```
/var/lib/loom/
├── envs/                     кэш окружений, переживает задачи
│   ├── py312-vllm-a1b2c3/        ключ = хеш спецификации среды
│   └── py312-torch-d4e5f6/
└── tasks/                    по каталогу на задачу, живёт пока живёт задача
    ├── inf-qwen-s1/
    │   ├── work/                 рабочая папка, квота
    │   └── out/                  сюда кладётся результат
    ├── train-run7/
    └── task-9f2a/
```

`envs/` и `tasks/` разделены намеренно: окружение дорогое и переиспользуемое,
каталог задачи дешёвый и одноразовый.

---

## 4. Жизненный цикл задачи

```
оркестратор                агент                     задача
     │
     │  RunTask ──────────→ │
     │                      │ 1. каталог: tasks/<id>/{work,out}
     │                      │ 2. вход: файлы клиента в work/
     │                      │ 3. среда: envs/<hash> — из кэша
     │                      │    или ставится и кэшируется
     │                      │ 4. запуск ───────────→ процесс
     │                      │                          │
     │  ← статус/логи ──────│ ← stdout по пайпу ───────│
     │                      │                          │
     │                      │ ← файлы в out/ ──────────│
     │                      │ 5. результат наружу      │
     │  ← Result ───────────│    (стрим или p2p)
     │                      │ 6. tasks/<id> снесён,
     │                      │    envs/<hash> остался
```

Разберём шаги, где есть тонкости.

### Шаг 2. Вход

Файлы задачи — код, конфиг, датасет — приезжают **через тот же исходящий
канал**, которым идёт всё остальное, и кладутся в `work/`. Отдельного порта,
отдельного протокола и отдельной аутентификации не появляется.

Это то, чего у воркера нет сегодня вообще: сейчас в задачу можно передать
только `env` и командную строку, из-за чего клиенту приходится запекать код в
образ.

### Шаг 3. Среда

Спецификация среды описывает, что должно оказаться в каталоге. Типов три,
и третий существует ровно потому, что первого недостаточно:

| тип | что делает | зачем |
|---|---|---|
| `python` | venv `--system-site-packages` + зависимости | обычный случай |
| `binary` | распаковать архив, запустить точку входа | не-Python нагрузки |
| `oci` | распаковать слои образа в каталог | любой язык, любые системные зависимости |

`--system-site-packages` даёт venv видеть то, что уже стоит в образе, — не
переустанавливать torch, если он есть. Ставится только то, чего не хватает.

`oci` — это то, ради чего обычно тянут Docker: универсальность образов. Мы
берём от неё нужное (распаковать и исполнить) и не берём ненужное (демон,
привилегии, вложенность).

**Кэш здесь не оптимизация, а условие работоспособности.** Без него мы
переносим гигабайты из `docker pull` в `pip install`, который медленнее, и
делаем холодный старт хуже, чем был. Ключ — хеш спецификации; окружение
переживает задачу; вытеснение по LRU в пределах квоты, которую задаёт
владелец. Первая инференсная задача на ноде ставит vLLM один раз, все
следующие стартуют мгновенно.

### Шаг 4. Запуск

Как именно исполняется задача — **сменный слой** под общим интерфейсом:

```
        каталог задачи + спецификация среды     ← общее
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   в каталоге     docker run      подпроцесс
   (основной)     (опция, нужен   (слабая изоляция,
                   доступ к докеру) опция владельца)
```

Всё, что выше — агент, стрим, туннель, p2p, оркестратор — не знает, какая
реализация сработала. Результат в любом случае оказывается в `out/`.

### Шаг 5. Результат

Наружу уходит через агента: либо по стриму до оркестратора, либо напрямую
соседу по p2p, если такой путь есть. Выбор делает `p2p/links.py` по тому же
правилу, что и для активаций инференса, — задача про это ничего не знает.

Логи идут отдельным потоком: stdout перехватывается пайпом, хранится хвост
ограниченного размера, отдаётся по запросу. Хвост, а не начало: конец
упавшего прогона говорит больше.

### Шаг 6. Уборка

`tasks/<id>` сносится целиком. Окружение остаётся в кэше.

## 5. Изоляция внутри контейнера

Здесь надо быть точным: **venv изолирует зависимости, а не процессы**.
Каталог задачи сам по себе ничего не защищает. Изоляция собирается из четырёх
вещей:

**Отдельный пользователь.** Задачи исполняются не от того пользователя, под
которым живёт агент. Каталог задачи принадлежит ей; чужие каталоги и файлы
агента не читаются.

**Чистое окружение.** Переменные среды агента содержат join key — credential
на всю ноду. Процесс задачи получает намеренно бедный набор без него.

**Лимиты.** `setrlimit` на память, число процессов и размер файла. Грубее
контейнерных, но закрывает форк-бомбу и утечку памяти.

**Снятие по таймауту.** Задача стартует в своей группе процессов, снимается
вся группа целиком — иначе умирала бы только верхняя оболочка.

Границей для владельца машины при этом остаётся **сам контейнер воркера**, и
это чище, чем сегодняшняя схема: вместо выдачи докер-сокета (то есть root на
хосте) мы обвешиваем флагами одну команду запуска, и всё, что внутри,
оказывается в этой коробке.

### Чего эта схема не даёт

Владельца машины защитить можно, клиента — нет. У владельца root на его
машине: он может прочитать память процесса, посмотреть, что на карте, и
подменить результат. Никакой набор флагов этого не меняет; помогло бы
конфиденциальное исполнение на уровне железа, которого на потребительских
картах нет. Работа, чья ценность — сами данные или веса, на такой парк
отдаваться не должна.

---

## 6. Что видит оркестратор

Ничего нового. Он по-прежнему шлёт команду по стриму `Attach`, получает
подтверждение и телеметрию. Контракт бэкендов не меняется.

Более того, хук уже есть и сегодня пуст:

```python
@abc.abstractmethod
def prepare(self) -> None:
```

Сейчас у всех бэкендов это `return None` — готовить нечего, среда вбита в
образ. Вся эта схема сводится к тому, что `prepare()` начинает делать свою
работу. Не переделка, а достройка.

---

## 7. Инференс и обучение как частные случаи

```
tasks/inf-qwen-s1/   → среда py312-vllm   → запускает shard/server.py
tasks/train-run7/    → та же среда        → запускает train/server.py
tasks/task-9f2a/     → среда клиента      → запускает код клиента
```

Разница только в спецификации среды и точке входа. Межстадийные сообщения,
туннель, p2p и таймингы остаются как есть: они не знают, что стадия теперь
живёт в каталоге, а не в образе.

Отсюда следует и порядок работ: инференс переводится **последним**, когда
механизм обкатан на задачах, падение которых ничего не стоит.

## 8. Чем это отличается от сегодняшнего

| | сейчас | цель |
|---|---|---|
| базовый образ | `vllm/vllm-openai` + наше | тонкий агент |
| инференс | вбит в образ | задача как все |
| compute | контейнер-брат через докер-сокет | каталог в своём контейнере |
| права на хосте | нужен сокет = root | ничего |
| вход задачи | только `env` и командная строка | файлы |
| результат | stdout, хвост 1 МБ | файлы через агента |
| не-Python нагрузки | только через образ | `binary` и `oci` |
| холодный старт | пул образа целиком | кэш окружений |

Отдельно: **compute-тракт сегодня на живой ноде не работает вовсе.** Команда
подключения из админки не монтирует `/var/run/docker.sock`, а в образе нет
докер-клиента, так что `available_runtime()` возвращает пустую строку и любая
задача получает отказ. Целевая схема этот блокер снимает не заплаткой, а тем,
что докер перестаёт быть нужен.

## 9. Открытые вопросы

**Проверить на живом железе, а не рассуждениями:**
во что реально обходится распаковка слоёв OCI без демона, и как ведёт себя
карта после сна машины — парк домашний, машины засыпают каждую ночь.

**Учёт GPU на ноде.** Несколько задач в одном контейнере делят карты, нужен
учёт занятых устройств. Сегодня в compute-тракте этого нет: устройства
назначаются как `0..N-1`, поэтому две одновременные задачи обе получают карту
0, пока остальные простаивают.

**Квота диска на каталог задачи** и вытеснение кэша окружений: без них чатная
задача забьёт диск владельца.

**Учёт трафика.** Задача с доступом в сеть тратит канал владельца без счёта.

---

## 10. Обновление воркеров

Тонкий образ окупается второй раз: если в образе почти ничего нет, то и
обновлять его почти никогда не нужно, а код агента можно обновлять по сети без
участия владельца. Отдельным документом — [WORKER_UPDATE.md](WORKER_UPDATE.md).

## 11. Порядок работ

1. Тонкая база + провижининг окружений с кэшем. Сердце всей схемы; пока его
   нет, остальное смысла не имеет.
2. Каталог задачи: отдельный пользователь, лимиты, квота, уборка.
3. Приём файлов и выдача результата через агента.
4. Перевод `compute` на новый механизм; докер-режим остаётся опцией для тех,
   кто готов дать сокет.
5. Тип среды `oci` — универсальность без демона.
6. Перевод `shard` и `train_shard` — последними.

Каждый шаг полезен сам по себе. Пятый и шестой можно менять местами; первые
четыре — нет.
