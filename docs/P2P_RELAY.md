# Circuit-relay: как соединить два воркера, до которых нельзя дозвониться

Дополнение к [P2P_TRANSPORT.md](P2P_TRANSPORT.md). Там описан прямой канал;
здесь — то, без чего он не поднимается для нод за NAT.

---

## 1. Задача

Машина за NAT может звонить наружу, но не может принимать. Поэтому воркер
достаёт оркестратора (звонит сам), а два воркера друг друга — нет: у обоих
входящие отбиваются.

Лечится **одновременным звонком**: оба бьют навстречу, каждый NAT запоминает
«мы говорим с тем адресом», и следующий пакет проходит. Но чтобы ударить
одновременно, надо договориться о моменте — а канала для этого нет, в том и
дело.

**Relay и есть этот канал.** Он даёт паре рабочее соединение, по которому они
синхронизируются и пробивают дырку, после чего соединение «схлопывается» в
прямое, и relay больше не нужен.

### Чем он отличается от релея через оркестратор

Вопрос законный: оркестратор тоже публично достижим и тоже пересылает.

| | релей оркестратора | circuit-relay |
|---|---|---|
| что пересылает | сообщения приложения — тензоры | само libp2p-соединение |
| как долго | всегда | секунды |
| зачем | доставить данные | **дать площадку договориться о прыжке** |
| после | ничего не меняется | пиры соединены напрямую |

Оркестратор — **пункт назначения**. Circuit-relay — **трамплин**.

---

## 2. Почему отдельный процесс

Оркестратор уже держит узел Lattica (rendezvous) и публично достижим. Казалось
бы, пусть он и будет relay.

Не может. Проверено на уровне протокола — вот что Lattica объявляет о себе в
identify:

```
/meshsub/1.1.0, /ipfs/id/1.0.0, /lattica/1.0.0, /ipfs/bitswap/1.2.0,
/rpc/req-resp/1.0.0, /ipfs/ping/1.0.0, /libp2p/circuit/relay/0.2.0/stop
```

`stop` — протокол **клиента** relay: «принять входящее через ретранслятор».
Протокола `hop`, который предоставляет **сервер**, нет. Конфигурации, которая
его включает, тоже нет: Rust-ядро молча принимает любые ключи, и ни один из
семи правдоподобных (`relay_server`, `enable_relay`, `relay_service`, …) ничего
не меняет.

Зато `stop` означает, что Lattica — **совместимый клиент circuit-relay v2**, и
ей нужен любой стандартный сервер. Им и стал `relay/relay.mjs` на js-libp2p.

У Parallax под это выделены отдельные хосты (`relay-lattica-*.gradient.network`)
ровно по той же причине: rendezvous и relay — разные роли.

---

## 3. Что это за сервис

`relay/relay.mjs`, ~60 строк на js-libp2p. Умеет ровно одно: принимать
резервации и пересылать соединения.

Чего в нём **нет** сознательно: DHT, прикладных протоколов, доступа к данным
моделей. Релеируемый поток шифруется из конца в конец между двумя воркерами (Noise), так
что этот процесс не может прочитать, что через него идёт.

Личность хранится в томе: её `peer_id` входит в каждый multiaddr, который
держат воркеры, и новая при каждом старте обесценила бы их все разом.

## 4. Как включить

Порт **47200 (TCP)** должен быть открыт снаружи — как и 47100 для rendezvous.
Воркерам по-прежнему открывать ничего не надо.

В `.env`:

```
LOOM_P2P_RELAY_PUBLIC_HOST=201.34.135.177
```

Поднять:

```bash
docker compose -f docker-compose.prod.yml up -d --build relay
```

В логе будет `peer_id` и адрес:

```
relay up: 12D3KooWQxXERB78dXxbfo8GRaW3sq3TAFcf8UM8if4h78SNggYN on port 47200
  /ip4/201.34.135.177/tcp/47200/p2p/12D3KooWQxXERB78dXxbfo8GRaW3sq3TAFcf8UM8if4h78SNggYN
```

Этот адрес целиком — в `.env`, и перезапустить оркестратор:

```
LOOM_P2P_RELAY=/ip4/201.34.135.177/tcp/47200/p2p/12D3KooW…
```

```bash
docker compose -f docker-compose.prod.yml up -d orchestrator
```

Дальше он сам раздаёт адрес воркерам в ответе на регистрацию, вместе с адресом
rendezvous. На воркерах ничего настраивать не нужно — только перезапустить,
чтобы они переподключились. Ручной способ, если воркер вне досягаемости
оркестратора: `LOOM_P2P_RELAY` в его окружении.

## 5. Ping: почему первая версия релея молча не работала

Первая версия поднималась, принимала соединения и выглядела здоровой. Резервация
бралась — и **пропадала через десять секунд**, после чего узел оставался
«не достучаться» навсегда. В логе воркера при этом ничего похожего на ошибку.

Причина в одной строке лога Lattica:

```
WARN lattica::network::core: Ping failed for peer 12D3KooW…: Unsupported
```

Lattica пингует всё, с чем соединена. Релей не объявлял `/ipfs/ping/1.0.0`,
отвечал «не поддерживаю» — и Lattica считала его мёртвым и рвала соединение.
Вместе с соединением умирала резервация. Дальше по кругу: переподключение,
пинг, разрыв.

Видно это только по адресам узла — вот один и тот же прогон до и после:

```
 t=0   visible: ['/ip4/…/p2p-circuit/p2p/12D3KooW…']     ← резервация есть
 t=10  visible: []                                        ← и больше не появится
```

```
 t=0…24  visible: ['/ip4/…/p2p-circuit/p2p/12D3KooW…']    ← с ping(), стабильно
```

Отсюда два следствия, оба уже в коде:

- в релее включён `ping()` — не украшение, а условие жизни резервации;
- воркер теперь пишет в лог, что именно с ним произошло: `reachable through
  the relay` при живой резервации, а при её отсутствии — разные сообщения для
  «релея не дали» и «релей дали, но резервации нет», потому что снаружи эти два
  случая неотличимы и лечатся по-разному.

В таблице узлов такое состояние отображается как **`peer через relay`**: узел
достижим, но только через ретранслятор. Это и есть признак, что релей работает.

## 6. Что проверено, а что нет

Проверено на этой машине:

| | |
|---|---|
| Lattica не может быть relay-сервером | ✅ доказано протоколом и перебором ключей конфига |
| Lattica объявляет `/libp2p/circuit/relay/0.2.0/stop` | ✅ совместимый клиент v2 |
| Lattica соединяется с js-libp2p relay | ✅ `Connection established … is_direct: true` |
| **Lattica берёт резервацию на этом релее** | ✅ circuit-адрес в `get_visible_maddrs()` |
| **резервация держится, а не отваливается** | ✅ после `ping()`; до него — 10 с |
| личность relay переживает перезапуск | ✅ |
| оркестратор раздаёт адрес, воркер его применяет | ✅ сквозным прогоном |

**Чего проверить нельзя локально:** что сосед действительно дозвонится через
circuit-адрес и что пробивание после этого удастся. На localhost AutoNAT
считает узел достижимым, резервация не берётся вовсе, и пиры находят друг
друга по обычным адресам — проверено, так и происходит. Нужны две машины за
настоящими разными NAT.

Признак успеха на стенде — метка сменится с `не достучаться` на
`peer через relay`, и доля прямых передач перестанет быть нулевой.

---

## 7. Ожидания

Пробивание NAT не всесильно: по данным статьи Lattica оно удаётся примерно в
**70% случаев**, остальное остаётся на relay. Симметричный NAT не пробивается
никогда — там адрес, по которому сосед стучится, заведомо не тот.

Так что часть пар останется на релее оркестратора, и это нормально: он
работает всегда и был единственным путём до сих пор.

Что делать, если после relay доля прямых всё равно нулевая:

1. посмотреть в логе воркера, сменилось ли `no address of this node is
   reachable from outside` — если нет, AutoNAT по-прежнему не подтверждает;
2. проверить, что 47200 действительно открыт: `nc -vz <хост> 47200`;
3. **самое надёжное — открыть 47100 на самих нодах.** Тогда пробивать нечего:
   нода просто достижима, и relay ей не нужен вовсе.
