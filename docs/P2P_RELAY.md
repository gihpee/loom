# Circuit-relay: как соединить два воркера, до которых нельзя дозвониться

Дополнение к [P2P_TRANSPORT.md](P2P_TRANSPORT.md). Там описан прямой канал;
здесь — то, без чего он не поднимается для нод за NAT.

---

## 1. Задача

Машина за NAT может звонить наружу, но не может принимать. Поэтому воркер
достаёт оркестратора (звонит сам), а два воркера друг друга — нет: у обоих
входящие отбиваются.

Лечится **одновременным звонком**: оба бьют навстречу, каждый NAT запоминает
«мы говорим с тем адресом», и следующий пакет проходит. Но чтобы ударить
одновременно, надо договориться о моменте — а канала для этого нет, в том и
дело.

**Relay и есть этот канал.** Он даёт паре рабочее соединение, по которому они
синхронизируются и пробивают дырку, после чего соединение «схлопывается» в
прямое, и relay больше не нужен.

### Чем он отличается от релея через оркестратор

Вопрос законный: оркестратор тоже публично достижим и тоже пересылает.

| | релей оркестратора | circuit-relay |
|---|---|---|
| что пересылает | сообщения приложения — тензоры | само libp2p-соединение |
| как долго | всегда | секунды |
| зачем | доставить данные | **дать площадку договориться о прыжке** |
| после | ничего не меняется | пиры соединены напрямую |

Оркестратор — **пункт назначения**. Circuit-relay — **трамплин**.

---

## 2. Почему отдельный процесс

Оркестратор уже держит узел Lattica (rendezvous) и публично достижим. Казалось
бы, пусть он и будет relay.

Не может. Проверено на уровне протокола — вот что Lattica объявляет о себе в
identify:

```
/meshsub/1.1.0, /ipfs/id/1.0.0, /lattica/1.0.0, /ipfs/bitswap/1.2.0,
/rpc/req-resp/1.0.0, /ipfs/ping/1.0.0, /libp2p/circuit/relay/0.2.0/stop
```

`stop` — протокол **клиента** relay: «принять входящее через ретранслятор».
Протокола `hop`, который предоставляет **сервер**, нет. Конфигурации, которая
его включает, тоже нет: Rust-ядро молча принимает любые ключи, и ни один из
семи правдоподобных (`relay_server`, `enable_relay`, `relay_service`, …) ничего
не меняет.

Зато `stop` означает, что Lattica — **совместимый клиент circuit-relay v2**, и
ей нужен любой стандартный сервер. Им и стал `relay/relay.mjs` на js-libp2p.

У Parallax под это выделены отдельные хосты (`relay-lattica-*.gradient.network`)
ровно по той же причине: rendezvous и relay — разные роли.

---

## 3. Что это за сервис

`relay/relay.mjs`, ~60 строк на js-libp2p. Умеет ровно одно: принимать
резервации и пересылать соединения.

Чего в нём **нет** сознательно: DHT, прикладных протоколов, доступа к данным
моделей. Релеируемый поток шифруется из конца в конец между двумя воркерами (Noise), так
что этот процесс не может прочитать, что через него идёт.

Личность хранится в томе: её `peer_id` входит в каждый multiaddr, который
держат воркеры, и новая при каждом старте обесценила бы их все разом.

---

## 4. Как включить

Порт **47200 (TCP)** должен быть открыт снаружи — как и 47100 для rendezvous.
Воркерам по-прежнему открывать ничего не надо.

Одна строка в `.env` — **хост**, по которому воркеры достают эту машину. Не
multiaddr: ни `/ip4/…`, ни порта, ни peer id. Просто адрес или имя.

```
LOOM_P2P_RELAY_PUBLIC_HOST=201.34.135.177
```

(Multiaddr сюда тоже можно — релей вытащит из него хост и скажет об этом в
логе. Раньше он на этом падал с `Protocol 201.34.135.177 was unknown`, и по
ошибке нельзя было понять, какая настройка виновата.)

И поднять:

```bash
docker compose -f docker-compose.prod.yml up -d --build relay
```

В логе:

```
relay up: 12D3KooWQxXERB78dXxbfo8GRaW3sq3TAFcf8UM8if4h78SNggYN on port 47200
  /ip4/201.34.135.177/tcp/47200/p2p/12D3KooWQxXERB78dXxbfo8GRaW3sq3TAFcf8UM8if4h78SNggYN
address published for the orchestrator: /data/relay/address
```

Последняя строка — весь второй шаг. Релей и оркестратор делят том, релей
пишет туда свой адрес, оркестратор читает его при каждой регистрации воркера.
Копировать multiaddr руками и перезапускать оркестратор не нужно; релей,
поднятый позже оркестратора, подхватится сам.

> Раньше этот шаг был ручным, и на живом стенде он потерялся ровно так, как
> и должен был: релей работал, воркеры работали, модель отвечала — а
> единственным следом был `(2 bootstrap, 0 relay)` в логе воркера, куда никто
> не смотрел. Поэтому шага больше нет.

Дальше оркестратор раздаёт адрес воркерам в ответе на регистрацию, вместе с
адресом rendezvous. На воркерах настраивать нечего — только перезапустить,
чтобы они переподключились.

Ручные варианты, когда они нужны: `LOOM_P2P_RELAY` в окружении оркестратора
(если релей стоит на другой машине — заданное значение всегда сильнее файла),
или `LOOM_P2P_RELAY` в окружении самого воркера.

## 5. Ping: почему первая версия релея молча не работала

Первая версия поднималась, принимала соединения и выглядела здоровой. Резервация
бралась — и **пропадала через десять секунд**, после чего узел оставался
«не достучаться» навсегда. В логе воркера при этом ничего похожего на ошибку.

Причина в одной строке лога Lattica:

```
WARN lattica::network::core: Ping failed for peer 12D3KooW…: Unsupported
```

Lattica пингует всё, с чем соединена. Релей не объявлял `/ipfs/ping/1.0.0`,
отвечал «не поддерживаю» — и Lattica считала его мёртвым и рвала соединение.
Вместе с соединением умирала резервация. Дальше по кругу: переподключение,
пинг, разрыв.

Видно это только по адресам узла — вот один и тот же прогон до и после:

```
 t=0   visible: ['/ip4/…/p2p-circuit/p2p/12D3KooW…']     ← резервация есть
 t=10  visible: []                                        ← и больше не появится
```

```
 t=0…24  visible: ['/ip4/…/p2p-circuit/p2p/12D3KooW…']    ← с ping(), стабильно
```

Отсюда два следствия, оба уже в коде:

- в релее включён `ping()` — не украшение, а условие жизни резервации;
- воркер теперь пишет в лог, что именно с ним произошло: `reachable through
  the relay` при живой резервации, а при её отсутствии — разные сообщения для
  «релея не дали» и «релей дали, но резервации нет», потому что снаружи эти два
  случая неотличимы и лечатся по-разному.

В таблице узлов такое состояние отображается как **`peer через relay`**: узел
достижим, но только через ретранслятор. Это и есть признак, что релей работает.

## 6. Что проверено, а что нет

Проверено на этой машине:

| | |
|---|---|
| Lattica не может быть relay-сервером | ✅ доказано протоколом и перебором ключей конфига |
| Lattica объявляет `/libp2p/circuit/relay/0.2.0/stop` | ✅ совместимый клиент v2 |
| Lattica соединяется с js-libp2p relay | ✅ `Connection established … is_direct: true` |
| **Lattica берёт резервацию на этом релее** | ✅ circuit-адрес в `get_visible_maddrs()` |
| **резервация держится, а не отваливается** | ✅ после `ping()`; до него — 10 с |
| личность relay переживает перезапуск | ✅ |
| оркестратор раздаёт адрес, воркер его применяет | ✅ сквозным прогоном |

**Чего проверить нельзя локально:** что сосед действительно дозвонится через
circuit-адрес и что пробивание после этого удастся. На localhost AutoNAT
считает узел достижимым, резервация не берётся вовсе, и пиры находят друг
друга по обычным адресам — проверено, так и происходит. Нужны две машины за
настоящими разными NAT.

Признак успеха на стенде — метка сменится с `не достучаться` на
`peer через relay`, и доля прямых передач перестанет быть нулевой.

---

## 7. Ожидания

Пробивание NAT не всесильно: по данным статьи Lattica оно удаётся примерно в
**70% случаев**, остальное остаётся на relay. Симметричный NAT не пробивается
никогда — там адрес, по которому сосед стучится, заведомо не тот.

Так что часть пар останется на релее оркестратора, и это нормально: он
работает всегда и был единственным путём до сих пор.

## 8. Релей — трамплин, а не канал данных

Это оказалось не философией, а работающим кодом или его отсутствием.

Когда релей заработал, произошло вот что: обе ноды взяли соединение через
circuit, пробивание не удалось, и **все активации пошли через релей**. Админка
показывала `peer 100% прямо`, а на деле:

| | через оркестратор | через circuit |
|---|---|---|
| транспорт на токен | ~200 ms | **320 ms** (81% времени) |
| скорость | ~5 tok/s | **2.5 tok/s** |

Логично: путь `воркер → релей → воркер` — те же два междугородних перехода, что
и через туннель оркестратора, только с ретранслятором общего назначения
посередине. Выигрыша нет по построению, есть потеря.

Хуже того, circuit-relay v2 применяет стандартные лимиты — **128 KB и две
минуты на соединение**. Для 4B-модели это 5120 байт на токен, то есть

```
131072 / 5120 ≈ 25 токенов
```

— после чего соединение рвётся и поднимается заново прямо посреди генерации.
Это и были `RPC call attempt 1 failed … retrying` в логах.

### Почему libp2p об этом не сказал

Потому что для него circuit — обычное соединение. Питоновский API Lattica не
отдаёт `is_direct` (в Rust-логах он есть, наружу не выведен), так что «связь
установлена» звучит одинаково в обоих случаях.

### Правило

Мерить, а не гадать. Релей стоит на машине оркестратора, поэтому дорога до
релея — это ровно первая половина дороги релеируемой активации. Отсюда:

> прямой канал используется, только если сосед **ближе, чем релей**.

Одно сравнение, и оно закрывает вопрос с circuit бесплатно: circuit идёт
*через* релей, значит не может быть быстрее релея. Никогда. А удавшееся
пробивание этот тест проходит.

Проверка повторяется раз в 30 с — DCUtR поднимает прямое соединение через
несколько секунд после первого звонка, и вердикт, вынесенный в тот момент, был
бы вердиктом о circuit. Если чисел нет (релея нет вовсе — тогда нет и circuit),
канал используется как раньше.

Лимиты в релее оставлены включёнными **намеренно**: они и есть то, что не даёт
ему стать каналом данных. Поднять их — значит спрятать симптом и оставить
медленный путь.

В таблице узлов это видно так:

```
relay  0% прямо
0/267
не выгодно: 180 ms против 60 ms до relay
```

## 9. Два транспорта и почему контейнер всё ломал

**Docker bridge.** Воркер на Linux запускался без `--network host`. Внутри
контейнера libp2p слушает `172.17.x.x:47100` — это не порт хоста, и каждый
исходящий пакет транслируется ещё раз, поэтому порт, в который соседу велено
целиться, не тот, на который что-то приходит. Опубликованного порта нет, так
что на хосте на 47100 не слушает никто: пробитый TCP-пакет встречает RST.

Пробивание из такого контейнера невозможно ни при каких условиях — ни релей,
ни DCUtR тут ни при чём, пакету некуда приземлиться. Поэтому `--network host`
теперь стоит и в документации, и в команде, которую выдаёт админка при
создании ключа, а воркер сам себя проверяет и пишет об этом в лог.

Port reuse, от которого пробивание зависит целиком, у Lattica **в порядке** —
проверено на живом узле, исходящее соединение идёт с порта прослушивания:

```
TCP 127.0.0.1:48201->127.0.0.1:48100 (ESTABLISHED)
```

**QUIC на релее.** Релей теперь слушает TCP и QUIC на одном номере. QUIC для
пробивания предпочтительнее: нет рукопожатия, которое stateful-файрвол может
оборвать RST, и нет проблемы одновременного открытия.

Но с оговоркой, которую стоит знать: **резервации Lattica берёт только по
TCP.** Проверено против этого релея — по QUIC она соединяется и просто не шлёт
`RESERVE`:

```
по TCP:   received RESERVE → creating new reservation
по QUIC:  соединение есть, RESERVE нет вовсе
```

Поэтому TCP-адрес публикуется первым, и оба вместе безопасны — Lattica берёт
TCP. QUIC-адрес в одиночку оставил бы воркер без слота.

Выигрыш от QUIC здесь не в резервации, а в самом прыжке: адреса для пробоя
пиры берут из **своих** объявлений, а там QUIC есть у обоих. Порт `47200/udp`
нужно открыть так же, как TCP.

## 10. Диагностика: работает ли релей с этой машины

Проверять релей через работающий воркер бесполезно: всё, что может сломаться,
выглядит одинаково — «прямого канала нет, релеим». Поэтому есть отдельная
проверка, поднимающая голый узел с одним только релеем:

```bash
python3 -m loom_worker.p2p.doctor /ip4/<хост>/tcp/47200/p2p/12D3KooW...
```

В контейнере воркера:

```bash
docker exec -it <контейнер> python3 -m loom_worker.p2p.doctor $LOOM_P2P_RELAY
```

Ответ один из трёх:

- `OK: the relay works from this machine` — слот взят и держится;
- `NO RESERVATION` — сюда релей недоступен: не запущен, закрыт порт или peer id
  в адресе от прежней личности релея;
- `RESERVATION LOST` — слот дали и отобрали; так выглядел релей без `ping()`.

Что смотреть в обычных логах:

```bash
docker compose -f docker-compose.prod.yml logs orchestrator | grep -i relay
```

`workers will be given 1 relay(s): …` — адрес роздан. `LOOM_P2P_RELAY is not
set` — оркестратор его не видит, и дальше искать нечего.

На воркере:

```bash
docker logs <контейнер> 2>&1 | grep -iE "p2p node up|relay|reachable"
```

`p2p node up: … (1 bootstrap, 1 relay)` — адрес дошёл. `reachable through the
relay` — резервация есть.

---

Что делать, если доля прямых нулевая и в логе нет «не выгодно»:

1. посмотреть в логе воркера, сменилось ли `no address of this node is
   reachable from outside` — если нет, AutoNAT по-прежнему не подтверждает;
2. проверить, что 47200 действительно открыт: `nc -vz <хост> 47200`;
3. **самое надёжное — открыть 47100 на самих нодах.** Тогда пробивать нечего:
   нода просто достижима, и relay ей не нужен вовсе.
